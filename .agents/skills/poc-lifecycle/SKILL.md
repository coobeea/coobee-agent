# POC 生命周期管理

标准化的需求全流程管理，每个阶段产出编号文件，覆盖从需求到 PR 的完整链路。

## 目录约定

```
<project-root>/pocs/
└── <requirement-name>/
    ├── 01-需求分析.md
    ├── 02-方案设计.md
    ├── 03-反思优化.md
    ├── 04-TODO.md
    ├── 05-PROGRESS.md
    └── 06-BUGS.md
```

- 目录名使用小写英文 + 短横线，如 `kb-api-protection`
- 所有文件使用中文书写
- 文件按阶段顺序编号，不可跳号

## 五阶段工作流

### 阶段一：需求分析 → 产出 `01-需求分析.md`

用户提出需求后：

1. 创建 `pocs/<name>/` 目录
2. 理解需求本质，提出澄清问题（如有必要）
3. 与用户确认需求理解无误
4. 将需求分析写入 `01-需求分析.md`，包含：
   - 需求背景
   - 核心目标
   - 约束条件
   - 涉及范围（模块、文件、接口等）

### 阶段二：方案设计 → 产出 `02-方案设计.md`

给出三个层次的方案：

| 层次 | 名称 | 特点 |
|------|------|------|
| 上策 | 最优方案 | 架构最优，长远收益高，实施成本较大 |
| 中策 | 平衡方案 | 兼顾质量和效率，推荐大多数场景 |
| 下策 | 最小方案 | 最快实现，适合紧急场景，可能留技术债 |

写入 `02-方案设计.md`，每个方案需包含：
- 核心思路
- 改动范围和影响评估
- 优劣对比

用户选定方案后，在文件末尾追加「选定方案」及理由。

### 阶段二与阶段四的边界

这两个阶段容易混淆，这里明确区分：

- **`02-方案设计.md`**：回答“为什么这样做、有哪些方案、选哪个更合适”
  - 重点是架构方向、模块边界、方案取舍、风险和收益
  - 不要求把实现任务拆到可以直接开工的粒度
- **`04-TODO.md`**：回答“接下来具体要做什么，谁接手都能直接做”
  - 本质上就是**实施前的详细设计 + 执行清单**
  - 要把任务拆到另一位工程师或智能体拿到后，不需要反复猜上下文，也能开始实施

如果 `02-方案设计.md` 还停留在方向层，而 `04-TODO.md` 仍然只是“优化一下”“整理一下”“支持一下”，说明拆分还不够细，不能进入实施阶段。

### 阶段三：反思优化 → 产出 `03-反思优化.md`

对选定方案进行自我审查，写入 `03-反思优化.md`：

1. 边界情况检查
2. 安全隐患评估
3. 对现有功能的影响
4. 性能和可维护性评估
5. 优化建议及最终方案调整

### 阶段四：实施计划 → 产出 `04-TODO.md` + `05-PROGRESS.md` + `06-BUGS.md`

根据前三个阶段确认的最终方案，创建三个执行跟踪文件：

**`04-TODO.md`** — 将方案拆解为**可以直接执行的详细设计任务**，每项必须尽量做到“脱离当前对话上下文也能理解”。每项至少应包含：
- 任务目标：这一项到底要解决什么问题
- 背景/原因：为什么要做这件事，解决哪个痛点
- 涉及范围：模块、目录、文件、接口
- 具体动作：明确到“改什么、加什么、删什么、同步什么”
- 非目标/边界（如有必要）：这项不处理什么
- 验收标准（可量化、可验证）
- 状态标记

**任务拆分要求：**

1. **每个 TODO 必须足够具体**
   - 不能只写“整理命名”“优化扩展机制”“支持 session command”
   - 要写清楚改哪些模块、动作是什么、结果长什么样

2. **每个 TODO 应尽量可独立执行**
   - 另一位工程师或智能体看到后，不应先去反推半天“你想让我改哪里”
   - 如果任务跨越多个职责，优先拆成多个 TODO

3. **TODO 名称优先写“对象 + 动作 + 范围”**
   - 好：`拆分 src/main/extension/types.ts 中的 Event / Interceptor 类型`
   - 好：`为 resources/extensions/session-commands 定义 manifest 结构和字段说明`
   - 差：`整理扩展类型`
   - 差：`完善命令系统`

4. **详细设计写在 TODO，不要只留在脑子里**
   - 如果实现依赖关键 rename、关键文件、关键边界判断，必须写进 TODO 描述
   - 不要假设后续执行者还能完整继承当前讨论上下文

5. **验收标准必须能判断完成与否**
   - 优先写“文件/类型/接口/测试/文档”的可见结果
   - 少写“逻辑更清晰了”“结构更合理了”这类无法验收的话

**`05-PROGRESS.md`** — 初始化，后续逐项执行时实时更新

**`06-BUGS.md`** — 初始化空模板，执行过程中记录问题

执行过程中：
- 每完成一个 TODO 项 → 更新 `04-TODO.md` 状态，在 `05-PROGRESS.md` 追加记录
- 遇到问题 → 记录到 `06-BUGS.md`，判断是否阻塞当前任务
- 发现新的待办 → 追加到 `04-TODO.md`

### TODO 拆分示例

以下示例说明什么叫“可执行的详细设计”。

#### 不推荐的写法

```markdown
### 1. 收敛 runtime 扩展命名

- **描述**：整理 runtime 扩展命名
- **验收标准**：
  - [ ] 命名更清晰
- **状态**：[ ]
```

问题：

- 看不出要改哪些文件
- 看不出哪些名字要改
- 看不出“清晰”如何判断
- 另一个智能体接手时，极易因为理解偏差而返工

#### 推荐的写法

```markdown
### 1. 整理 runtime 扩展 API 的分类和命名

- **目标**：把 runtime 扩展点明确拆成 Event 和 Interceptor，避免旧名字继续误导实现和文档。
- **背景**：当前 `before_* / session_* / agent_end` 混合了通知事件、可修改拦截点和 run 生命周期语义，读代码时容易误判。
- **涉及范围**：
  - `src/main/extension/types.ts`
  - `src/main/extension/ExtensionApi.ts`
  - `src/main/extension/ExtensionHookRunner.ts`
  - 相关调用点和文档
- **具体动作**：
  - 在 `types.ts` 中显式区分 `Event` 和 `Interceptor`
  - 将 `before_agent_start` 改为 `prepare_run_input`
  - 将 `before_tool_call` 改为 `prepare_tool_call`
  - 将 `tool_result_persist` 改为 `transform_tool_result`
  - 将 `session_start` 改为 `run_started`
  - 将 `agent_end` 改为 `run_completed`
  - 将 `before_compaction` 改为 `compaction_started`
  - 同步更新调用点、类型和文档
- **非目标**：
  - 本项不引入新的 UI 入口
  - 本项不实现 session command loader
- **验收标准**：
  - [ ] `types.ts` 里能明显看出哪些是 `Event`，哪些是 `Interceptor`
  - [ ] 上述 rename 已在调用点完成同步
  - [ ] 文档与代码中的命名一致
- **状态**：[ ]
```

标准判断：

- 看一眼就知道要做什么
- 知道改哪里
- 知道不改哪里
- 做完后可以直接验收

### 阶段五：PR 提交

1. 确认 `04-TODO.md` 全部完成
2. 确认 `06-BUGS.md` 中无未解决的阻塞问题
3. 更新 `05-PROGRESS.md` 标记为「已完成」
4. 创建 Git 分支（如未创建）
5. 提交代码并创建 PR，PR 描述中引用 pocs 目录

## 执行规则

1. **每个阶段必须产出对应编号的文件**，不可跳过
2. **进入实施前，`04-TODO.md` 必须达到可执行的详细设计粒度**
3. **如果另一个工程师或智能体看到 TODO 仍不知道“改哪里、怎么验收”，说明拆分不合格，需要继续细化**
4. **每完成一个 TODO 项**，立即更新 `04-TODO.md` 和 `05-PROGRESS.md`
5. **遇到问题时**，先记录到 `06-BUGS.md`，再决定是否阻塞当前任务
6. **每次会话开始时**，检查 `pocs/` 下是否有进行中的需求，读取文件恢复上下文
7. **目录名一旦创建不要更改**，避免引用失效

## 快速命令

| 用户指令 | 操作 |
|---------|------|
| "新需求：xxx" | 进入阶段一，创建目录，产出 `01-需求分析.md` |
| "出方案" | 进入阶段二，产出 `02-方案设计.md` |
| "选上策/中策/下策" | 进入阶段三，产出 `03-反思优化.md` |
| "开始实施" | 进入阶段四，产出 `04/05/06` 三个文件并开始执行 |
| "看一下进度" | 读取并展示 `04-TODO.md` 和 `05-PROGRESS.md` |
| "有什么问题" | 读取并展示 `06-BUGS.md` |
| "提交 PR" | 进入阶段五 |
