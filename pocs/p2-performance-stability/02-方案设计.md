# P2 - 性能与稳定性优化：方案设计

## 1. 整体策略

采用**分阶段、低风险**的渐进式优化策略，优先处理影响面小、收益明显的改动。

## 2. P2-1: 同步 IO 异步化

### 上策：分层异步化（推荐） ⭐

**设计思路**：  
将同步 IO 分为三个优先级，逐步改造：

#### 第一层：事件写盘（高优先级）
- **目标**：`EventWriter` 和 `HistoryWriter` 异步化
- **方案**：
  1. 引入内存队列（基于 `async-queue` 或手写轻量队列）
  2. 事件先写入队列，后台定期（或达到批次大小时）flush 到磁盘
  3. 提供 `flush()` 接口，在关键节点（会话结束、应用退出）强制落盘
  4. 保持接口兼容（或提供 sync/async 两个版本）

**实现要点**：
```typescript
class AsyncEventWriter {
  private queue: StreamChunk[] = [];
  private flushing = false;
  private flushInterval = 100; // ms

  async write(chunk: StreamChunk): Promise<void> {
    this.queue.push(chunk);
    
    // 达到批次大小或超时时触发 flush
    if (this.queue.length >= 10 || !this.flushing) {
      await this.flush();
    }
  }

  private async flush(): Promise<void> {
    if (this.flushing || this.queue.length === 0) return;
    
    this.flushing = true;
    const batch = this.queue.splice(0, this.queue.length);
    
    try {
      await fs.promises.appendFile(this.filePath, this.serialize(batch));
    } finally {
      this.flushing = false;
    }
  }
}
```

**优点**：
- 影响面小，只改事件写入路径
- 性能提升明显（高频场景）
- 可以逐步迁移，不破坏现有代码

**缺点**：
- 需要处理队列满、崩溃丢失等边界情况
- 需要额外的测试验证

---

#### 第二层：Store 查询（中优先级，可选）
- **目标**：`ThreadStore.list()` 和 `AgentStore.rebuildIndex()` 异步化
- **方案**：
  1. 提供 `listAsync()` 和 `rebuildIndexAsync()` 新接口
  2. 逐步迁移调用方
  3. 旧接口标记 `@deprecated`，给出迁移指引

**实现要点**：
```typescript
// 新接口（异步）
async listAsync(filter?: ThreadListFilter): Promise<ThreadIndexEntry[]> {
  await this.init();
  const entries = Array.from(this.index.values());
  // ...
}

// 旧接口（保持兼容，标记废弃）
@deprecated('Use listAsync() instead')
list(filter?: ThreadListFilter): ThreadIndexEntry[] {
  // 调用异步版本，但阻塞等待
  return this.listAsync(filter).then(...);
}
```

**优点**：
- 渐进式迁移，兼容性好
- 批量读取场景性能提升

**缺点**：
- 需要修改调用方（API 变动）
- 短期内需要维护两套接口

---

#### 第三层：Worker 方案（低优先级，可选）
- **目标**：将事件落盘完全迁移到 Worker 线程
- **方案**：
  1. 创建专用的 `EventWriterWorker`
  2. 主线程通过 `postMessage` 发送事件
  3. Worker 内部负责批量写入

**优点**：
- 完全隔离 IO 操作
- 主线程零阻塞

**缺点**：
- 架构复杂度增加
- 序列化开销（需要传递 `StreamChunk`）
- 调试难度上升

**结论**：暂不推荐，除非高频场景仍有明显阻塞。

---

### 中策：仅优化批量操作

**设计思路**：  
只改造 `ThreadStore.list()` 等批量读取路径，事件写入保持同步。

**优点**：
- 风险最低
- 改动最小

**缺点**：
- 收益有限（高频写入场景仍会阻塞）

---

### 下策：不改（保持现状）

**理由**：  
如果当前性能可接受，且没有明显用户投诉，可以暂缓改造。

## 4. P2-3: Skill 缓存失效

### 方案：Hook Extension 生命周期（推荐） ⭐

**设计思路**：  
在 Extension 加载/卸载/watch 事件时，主动调用 `SkillManager.invalidateCache()`。

**实现要点**：
```typescript
// ExtensionLoader.ts
async loadAll(searchPaths: string[]): Promise<void> {
  // ...加载逻辑...
  
  // 加载完成后失效缓存
  const { SkillManager } = await import('../skills/SkillManager');
  SkillManager.getInstance().invalidateCache();
}

// ExtensionLoader watch 事件
watcher.on('change', (path) => {
  // ...重新加载 Extension...
  
  // 失效缓存
  SkillManager.getInstance().invalidateCache();
});
```

**优点**：
- 改动小，风险低
- 立即生效，热重载体验提升

**缺点**：
- 需要在多个地方调用（load/unload/watch）
- 可能增加一些性能开销（需要监控）

---

### 备选方案：缓存键加版本号

**设计思路**：  
缓存键中加入目录 `mtime` 或 Extension `manifest.version`。

**优点**：
- 自动失效，无需手动调用

**缺点**：
- 需要读取文件 mtime（额外 IO）
- 复杂度稍高

---

## 5. 技术选型

### 异步队列库
- **推荐**：手写轻量队列（避免引入新依赖）
- **备选**：`p-queue`（如果需要更复杂的调度策略）

### 测试策略
- **单元测试**：验证异步写入逻辑正确性
- **集成测试**：验证高频写入场景性能
- **压力测试**：模拟 >100 events/s 的写入

---

## 6. 实施顺序

1. **P2-2**：CoreSkills 清理（最低风险，快速完成）
2. **P2-3**：Skill 缓存失效（低风险，改善开发体验）
3. **P2-1**：事件写盘异步化（中风险，需要充分测试）
4. **（可选）P2-1 第二层**：Store 异步化（低优先级）

---

## 7. 回滚计划

- P2-2: 如有问题，重新添加 CoreSkills（通过 git revert）
- P2-3: 移除缓存失效调用
- P2-1: 保留同步版本接口，切换回旧实现

## 8. 性能监控

### 关键指标
- 主线程占用率（`performance.now()` 跨度）
- 事件写入延迟（队列长度）
- 批量查询耗时（`ThreadStore.list()` 耗时）

- 增加性能日志（`log.perf()`）
