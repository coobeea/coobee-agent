# TS Harness 移植 - 方案设计

> 创建时间：2026-07-28
> 约束：仅实现 `src/main/harness/`，不改动、不接入任何其他代码

## 设计原则（三策共用）

1. **Harness 长驻 / Runner 按轮** — 对齐 Go：`New → NewRunner → Run`
2. **Orchestrator 拥有生命周期** — Agent 只做 `describeRun` + `stream`
3. **OOP** — class / interface / 依赖注入；不用包级函数堆叠
4. **依赖单向** — `agent` 不依赖 `extension`；Hook 由 orchestrate / tools 调度
5. **隔离** — harness 内自建全部契约，零外部 import（除 Node/TS 标准库）

---

## 上策：完整内核对齐移植

- **核心思路**：按 Go 模块地图几乎全量落地（orchestrate 四阶段实装、hook 闭集 21 个、event bus、session FileStore、tool pipeline、spawn 嵌套、prompt 组装、config profile），Agent 先用 Mock/Stub，整条 Run 可端到端跑通。
- **改动范围**：仅 `src/main/harness/**`，文件量大（预计 80+ 文件）
- **优势**：与 Go SSOT 对齐最深；后续接入成本最低；行为可对照 Go 测试
- **劣势**：第一版周期长；很多子系统（session 落盘、spawn、compaction）在「未接入」前提下价值有限；容易过度设计

---

## 中策：OOP 骨架 + 可运行的最小编排（推荐）

- **核心思路**：先落地**分层骨架与核心契约**，并把 Orchestrator 四阶段（head → prepare → stream → finish）做成**真实可调用的最小实现**；Agent / Session / Emitter / HookRunner 提供可替换的 stub 默认实现，使 `Harness.newRunner().run(signal)` 能跑通一条空链路。prompt / spawn / config / builtin tools 只留目录与接口占位。
- **改动范围**：仅 `src/main/harness/**`，约 25–40 个文件
- **优势**：边界清晰、可编译、可单测；实现量可控；后续可按模块增量填肉；不碰现有系统
- **劣势**：与 Go 行为不完全等价；Extension Loader / FileStore / ToolPipeline 细节后补

### 核心类关系

```text
Harness (process-long)
  ├── SessionStore
  ├── EventBus
  ├── ExtensionSubsystem (HookRunner, Registry, Loader)
  ├── ToolRegistry
  └── AgentFactory
        │
        ▼ NewRunner(config)
Runner (per-turn)
  ├── Orchestrator
  ├── Agent          // Identity 已冻结
  ├── RunDeps        // { sessions, emitter, hooks, logger }
  └── RunnerConfig
        │
        ▼ run(signal)
DefaultOrchestrator
  head → prepare → stream → finish
```

### 关键 OOP 映射

| Go                         | TS                                                            |
| -------------------------- | ------------------------------------------------------------- |
| `harness.Harness`          | `class Harness`                                               |
| `runner.Runner`            | `class Runner`                                                |
| `orchestrate.Orchestrator` | `interface Orchestrator` + `class DefaultOrchestrator`        |
| `agent.Agent`              | `interface Agent` + `class StubAgent`                         |
| `agent/engine.Factory`     | `class AgentFactory`                                          |
| `extension.Wired`          | `class ExtensionSubsystem`                                    |
| `hook.Runner`              | `interface HookRunner` + `class NoopHookRunner`               |
| `event.Emitter`            | `interface Emitter` + `class NoopEmitter` / `StandardEmitter` |
| `session.SessionStore`     | `interface SessionStore` + `class InMemorySessionStore`       |
| `tools.ToolRegistry`       | `class ToolRegistry`                                          |

### 第一版 Orchestrator 最小行为

| 阶段      | 行为                                                                      |
| --------- | ------------------------------------------------------------------------- |
| `head`    | 调 void hook `message_received`；Emitter 发 `user:input`（noop 可空操作） |
| `prepare` | 调 modifying hooks（可全 noop）；`agent.describeRun(input)`               |
| `stream`  | 调 void `run_started`；消费 `agent.stream`；维护 `RunState`               |
| `finish`  | 成功路径：emit `run:done`；返回 assistant 终稿                            |

失败 / 取消 / block / short_reply 先留方法骨架，成功路径打通即可。

---

## 下策：纯类型契约 + 空壳类

- **核心思路**：只定义 interface / type / 空 class 方法签名，全部 `throw new Error('not implemented')` 或空返回；目录对齐 Go。
- **改动范围**：仅 `src/main/harness/**`，约 15–25 个文件
- **优势**：最快落地边界；讨论成本低
- **劣势**：无法验证分层是否跑得通；后续填肉时容易发现契约设计有误；对「先搞一版」价值偏弱

---

## 方案对比

| 维度       | 上策               | 中策           | 下策         |
| ---------- | ------------------ | -------------- | ------------ |
| 实施成本   | 高                 | 中             | 低           |
| 长期收益   | 高                 | 高             | 中           |
| 可验证性   | 强（e2e）          | 强（最小 Run） | 弱           |
| 风险       | 过度实现、周期失控 | 低             | 契约设计返工 |
| 与约束契合 | 契合但偏重         | **最契合**     | 契合但偏薄   |

## 选定方案

选定 **上策：完整内核对齐移植**。

理由（2026-07-28 确认）：

1. **功能要全亮** — 对齐 Go harness 的完整能力面（编排四阶段、hook 闭集、event、session、tools、spawn、prompt、config），不只做空壳
2. **OOP** — TypeScript 面向对象设计（class / interface / 依赖注入）
3. **隔离** — 不看、不改、不接项目内现有 `agent/` / `extension/` 等实现；只参考 vessel Go harness
4. **最小层** — 把 harness 作为独立内核层完整实现；不向上对接应用层
