# TS Harness 移植 - 反思优化

> 创建时间：2026-07-28
> 选定方案：上策（完整内核对齐 + OOP + 隔离实现）

## 边界情况

1. **Signal / 取消**：AbortSignal 映射 Go `context.Context`；取消路径必须走 `finishCancelled`，不能抛未处理异常
2. **并发 Turn**：每次 `NewRunner` 独立 `RunDeps` / Emitter / Agent；禁止共享可变 RunState
3. **Hook 失败**：void/soft 不阻断；modifying 按 merge 规则；`run_completed` / `subagent_ended` SoftTimeout
4. **空 SessionStore**：`New` 必须校验注入；第一版提供 `FileSessionStore` + 测试用 `InMemorySessionStore`
5. **工具未注册**：`RegisterAllTools` 由调用方显式触发，与 Go 一致
6. **子 Turn**：spawn 必须走 `RunnerCreator → NewRunner`，不得私开 Agent 循环

## 安全评估

1. 路径工具需 workspace 边界校验（对齐 Go `tools/path`）
2. `exec` / `process` 需可控 cwd 与超时；第一版实现能力，策略默认偏严
3. Extension Loader 只加载 harness 约定路径下的模块；不触达项目现有 extension 目录逻辑
4. API Key / 模型凭据只经 Options / ModelProvider 注入，不写死

## 影响分析

- **对本仓库现有功能：零影响**（不改、不接任何现有模块）
- harness 自成命名空间 `src/main/harness/**`
- 未来接入是另一 POC；本 POC 不预埋对 `AgentExecutor` 的引用

## 性能与可维护性

- OOP 分层清晰，长期可维护性高于当前散落执行链
- EventBus 进程内同步/异步消费者与 Go 对齐；磁盘消费者可后挂
- 上策体量大：按依赖分层分阶段交付，每阶段可编译、可单测

## 优化调整

相对原「上策」文档，补充执行策略：

1. **功能全亮，分层交付**：对外承诺完整能力面；对内按 Phase 0→7 依赖序实现，先打通「最小可运行内核层」，再填 builtins / spawn / 后端
2. **只参考 vessel Go**：不阅读、不复用 `src/main/agent` / `extension` 等现有实现
3. **OOP 强制**：每个子系统以 class/interface 表达；Orchestrator 四阶段为方法，不是巨型 switch
4. **AsyncIterable 替代 Go iter.Seq2**：`Agent.stream()` 返回 `AsyncIterable<StreamEvent>`
5. **RunStore**：用 `AsyncLocalStorage`（或显式参数传递）替代 Go context value

## 最终方案

在 `src/main/harness/` 用 TypeScript OOP **完整移植** vessel Go harness 内核：

```text
Harness.New → NewRunner → Runner.Run(signal)
  → DefaultOrchestrator: head → prepare → stream → finish*
```

覆盖：types / logger / event / session / tools / extension / config / prompt / model / agent / orchestrate / runner / spawn / harness 入口。

交付节奏：先实现**依赖底层 + 编排心跳 + StubAgent 跑通 Run**（最小内核层），再补全 builtin、真实 LLM Agent、spawn、FileStore 细节，直至功能全亮。全程不对接项目其他代码。
