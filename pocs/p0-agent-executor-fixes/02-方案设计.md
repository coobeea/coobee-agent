# Agent Executor P0 问题修复 - 方案设计

> 创建时间：2026-04-22

## 问题拆解

本次修复包含两个独立问题，可以分别设计方案：

1. **P0-1**：`builderProjectDir` 未定义导致编译错误
2. **P0-2**：Thread 恢复路径配置不完整

## P0-1 方案：修复 builderProjectDir 编译错误

### 上策：引入 projectDir 语义并完整实现

**核心思路**：
- 承认"项目目录（projectDir）" 和 "工作空间（workspace）" 是两个不同的概念
- 在 Builder 中增加 `projectDir()` 方法
- 在 `AgentEnvInjector` 中从 Builder 读取 `projectDir`
- 工具执行时优先使用 `projectDir`，回退到 `workspace`

**改动范围**：
- 新增 `BaseAgentBuilder.projectDir()` 方法
- 新增 `BaseAgentBuilder.getProjectDir()` getter
- `AgentEnvInjector` 中通过 `builder.getProjectDir()` 获取值
- 可能需要在 Thread/Agent 定义中增加 `projectDir` 字段

**优势**：
- 语义清晰：明确区分"Agent 工作空间"和"用户项目目录"
- 扩展性好：未来支持"一个 Agent 操作多个项目"更容易
- 架构完整：不留技术债

**劣势**：
- 改动范围大，需要修改多个模块
- 需要定义清晰的语义（什么时候用 workspace，什么时候用 projectDir）
- 可能引入新的概念混乱（如果定义不清）
- P0 修复不应该引入新概念

### 中策：移除 builderProjectDir，统一使用 workspace

**核心思路**：
- 承认 `builderProjectDir` 是一个遗留变量，应该被移除
- 所有地方统一使用 `workspace` 作为工作根目录
- 在注释中说明：当前不区分"项目目录"和"工作空间"，两者等同

**改动范围**：
- 修改 `AgentEnvInjector.ts` 第 211、227 行：
  ```typescript
  // 修改前
  const effectiveCwd = builderProjectDir || workspace;
  
  // 修改后
  const effectiveCwd = workspace;
  ```
- 增加注释说明当前的设计决策

**优势**：
- 改动最小，风险最低
- 不引入新概念，不增加复杂度
- 符合 P0 "止血优先" 原则
- 当前生产环境已经这样运行（因为 `builderProjectDir` 一直是 undefined）

**劣势**：
- 没有为未来的"多项目支持"预留扩展点
- 如果原设计确实需要区分两个概念，这个方案是"欠债"

### 下策：用条件编译暂时屏蔽

**核心思路**：
- 使用 TypeScript 的 `any` 或 `@ts-ignore` 暂时屏蔽编译错误
- 不修改逻辑，只让编译通过

**改动范围**：
```typescript
// @ts-ignore builderProjectDir 暂时未定义，待重构
const effectiveCwd = builderProjectDir || workspace;
```

**优势**：
- 改动极小，几乎零风险
- 不影响运行时行为

**劣势**：
- 治标不治本，技术债累积
- 违背代码质量原则
- 未来重构时仍需处理

## P0-2 方案：统一 Thread 恢复路径

### 上策：抽取 ThreadExecutionFactory 统一配置逻辑

**核心思路**：
- 新建 `ThreadExecutionFactory` 类
- 提供 `buildFromThread(threadId)` 方法，返回完整配置的 Builder
- `ChatRoutes` 和 `ThreadWaker` 都调用这个工厂方法

**改动范围**：
- 新增 `src/main/agent/threads/ThreadExecutionFactory.ts`
- 重构 `ChatRoutes.sendMessage()` 的 Builder 配置逻辑
- 重构 `ThreadWaker.submitResumeMessage()` 的 Builder 配置逻辑

**优势**：
- 彻底消除重复代码
- 保证两条路径完全一致
- 为后续扩展提供清晰的扩展点
- 符合架构评审文档的建议

**劣势**：
- 改动范围大，涉及核心执行路径
- 需要充分的测试覆盖
- 可能引入回归风险
- **超出 P0 "最小改动" 原则**

### 中策：在 ThreadWaker 中复制 ChatRoutes 的配置逻辑

**核心思路**：
- 保持 `ChatRoutes` 不变
- 在 `ThreadWaker.submitResumeMessage()` 中复制 `ChatRoutes` 的 Builder 配置代码
- 确保两处逻辑完全一致

**改动范围**：
- 修改 `src/main/agent/threads/ThreadWaker.ts:165-167`：
  ```typescript
  // 修改前
  const builder = agentExecutor.piMono();
  
  // 修改后
  const thread = await ThreadStore.getInstance().then(s => s.get(threadId));
  const agent = await AgentStore.getInstance().then(s => s.get(thread.agentId));
  
  const builder = agentExecutor.piMono().sessionMode('file').name(agent.id);
  
  const modelSpec = thread.overrideModel || agent.model;
  if (modelSpec) {
    agentExecutor.applyProviderConfig(builder, { 
      modelOverride: modelSpec,
      sessionId: threadId,
      agentId: agent.id
    });
  }
  
  if (agent.instructions !== undefined) {
    builder.instructions(agent.instructions);
  }
  ```

**优势**：
- 改动范围小，只修改 `ThreadWaker`
- 不影响现有的正常执行路径
- 立即解决问题，无需大规模重构
- 符合 P0 修复原则

**劣势**：
- 代码重复（ChatRoutes 和 ThreadWaker 各有一份）
- 未来修改时需要同步两处
- 留下技术债（需要在 P1 阶段抽取工厂）

### 下策：在 ThreadWaker 中只补充最关键的配置

**核心思路**：
- 只补充最容易遗漏的配置项：`sessionMode('file')`
- 其他配置项（model、instructions）暂时不处理

**改动范围**：
```typescript
const builder = agentExecutor.piMono().sessionMode('file');
```

**优势**：
- 改动极小，几乎无风险
- 至少能保证会话持久化

**劣势**：
- 没有彻底解决问题
- model 和 instructions 仍然不一致
- 用户恢复会话时仍可能遇到问题

## 组合方案对比

由于 P0-1 和 P0-2 是独立问题，可以分别选择方案：

| 组合 | P0-1 | P0-2 | 总体评估 |
|------|------|------|---------|
| **推荐** | 中策（移除 builderProjectDir） | 中策（复制配置逻辑） | 最小改动，立即解决问题 |
| 激进 | 上策（引入 projectDir） | 上策（抽取 Factory） | 架构最优，但风险高 |
| 保守 | 下策（暂时屏蔽） | 下策（只补充 sessionMode） | 风险最低，但留债最多 |

### 推荐组合：P0-1 中策 + P0-2 中策

**总体改动**：
1. `AgentEnvInjector.ts`：移除 `builderProjectDir`，使用 `workspace`
2. `ThreadWaker.ts`：复制 `ChatRoutes` 的 Builder 配置逻辑

**实施成本**：低
**风险等级**：低
**技术债**：中等（需要在 P1 阶段抽取 Factory）

**为什么不选上策**：
- P0 修复的首要目标是"止血"，不是"架构完美"
- 上策涉及引入新概念（projectDir）或新抽象（Factory），需要更充分的设计和测试
- 当前问题不值得承担上策的风险

**为什么不选下策**：
- 下策没有真正解决问题，只是掩盖
- P0 问题已经影响用户，不能继续拖延

---

## 选定方案

**选择：P0-1 中策 + P0-2 中策**

### 理由

1. **符合 P0 原则**：最小改动，快速止血
2. **风险可控**：只修改 2 个文件，不引入新抽象
3. **立即见效**：修复后编译通过，恢复路径正确
4. **技术债可控**：重复代码可以在 P1 阶段重构（见 agent-module-review.md 第二阶段）

### 具体实施

#### P0-1 修复步骤

1. 修改 `src/main/agent/AgentEnvInjector.ts`
2. 将 211 和 227 行的 `builderProjectDir || workspace` 改为 `workspace`
3. 增加注释说明当前不区分 projectDir 和 workspace
4. 运行 `pnpm typecheck` 验证修复

#### P0-2 修复步骤

1. 修改 `src/main/agent/threads/ThreadWaker.ts`
2. 在 `submitResumeMessage()` 中补充完整的 Builder 配置
3. 参考 `ChatRoutes.sendMessage()` 的实现
4. 写一个简单的集成测试验证恢复路径正确性

### 后续改进

修复完成后，应该在 P1 阶段：
1. 抽取 `ThreadExecutionFactory`
2. 消除 ChatRoutes 和 ThreadWaker 的代码重复
3. 明确 workspace / projectDir 的语义，如果需要区分则实施 P0-1 上策

这些改进记录在 `agent-module-review.md` 第二阶段中。
