# ASR Provider 架构拆分 - 方案设计

> 创建时间：2026-05-04

## 上策：完整分层 + Provider 接口体系

- **核心思路**：
  - 在 `resources/workers/asr/` 下建立清晰目录：
    - `core/`：配置、协议、日志、会话上下文、公共工具
    - `providers/`：不同 ASR provider 的实现
    - `app/`：入口与 provider 选择
  - 定义统一抽象，例如：
    - `BaseAsrProvider`
    - `AsrSessionContext`
    - `TranscriptEmitter`
  - 本地 ASR、阿里云 ASR 都实现相同接口，对外统一产出 transcript 事件。
- **改动范围**：
  - `server.py` 大幅瘦身
  - 新增多个 Python 文件
  - 需要同步整理通用工具函数归属
- **优势**：
  - 架构最清晰，长期收益最高
  - 最适合后续接入更多 provider
  - provider 可单独测试、单独排障
- **劣势**：
  - 首次拆分成本较大
  - 需要一次性梳理较多通用能力边界

## 中策：保留单入口，抽出 Provider 实现文件

- **核心思路**：
  - 保留 `server.py` 作为唯一入口文件
  - 先把阿里云、本地 ASR 各自拆到独立文件
  - 把 transcript 协议、日志、公共工具抽到 `common.py` / `protocol.py` / `utils.py`
  - `server.py` 只负责：
    - 启动
    - provider 选择
    - 路由转发到对应实现
- **改动范围**：
  - `server.py` 中度重构
  - 新增 4-8 个辅助文件
  - 对当前逻辑侵入适中
- **优势**：
  - 风险可控
  - 能明显降低单文件复杂度
  - 不会一次引入过重的框架设计
- **劣势**：
  - 通用抽象可能还不够彻底
  - 如果后续 provider 继续增多，仍可能需要再做一次升级

## 下策：只做函数级拆分，不引入 Provider 抽象

- **核心思路**：
  - 仅把 `server.py` 里的大函数拆到多个文件
  - 仍然通过条件分支选择本地 / 阿里云实现
  - 不建立统一 provider 接口
- **改动范围**：
  - 主要是代码搬运
  - 结构变化小
- **优势**：
  - 最快
  - 对现有逻辑影响最小
- **劣势**：
  - 只是“文件变多”，不是“架构变清晰”
  - 后续继续接新 provider 时，扩展性仍然一般
  - 很容易再次回到“分散但仍耦合”的状态

```text
resources/workers/asr/
├── server.py
├── app/

│   └── provider_registry.py
```

## 建议接口形态

### 1. Provider 抽象

```python
class BaseAsrProvider:
    name: str

    async def startup(self) -> None:
        ...

    async def health(self) -> dict:
        ...

    async def handle_ws(self, ws: WebSocket) -> None:
        ...
```

### 2. Transcript 输出器

```python
class TranscriptEmitter:
    async def send_status(self, ws: WebSocket, status: str, **payload) -> bool:
        ...

    async def send_transcript(
        self,
        ws: WebSocket,
        *,
        provider: str,
        transcript_event: str,
        committed: str,
        draft: str = "",
        turn_id: str = "",
        revision: int = 0,
        is_final_turn: bool = False,
        is_final_session: bool = False,
        **payload,
    ) -> bool:
        ...
```

### 3. Session Context

```python
@dataclass
class AsrSessionContext:
    committed_text: str = ""
    current_turn_id: str = ""
    current_revision: int = 0
    transcript_seq: int = 0
```

## 方案对比

| 维度 | 上策 | 中策 | 下策 |
|------|------|------|------|
| 实施成本 | 高 | 中 | 低 |
| 长期收益 | 高 | 中高 | 低 |
| 风险 | 中 | 低中 | 低 |
| 可扩展性 | 高 | 中高 | 低 |
| 可维护性 | 高 | 中高 | 中低 |

## 选定方案

选择 **中策**。

理由：

- 当前 ASR 还在排障期，先做“入口保留 + provider 拆文件”更稳
- 能先把 `server.py` 的责任压缩下来，同时保留现有行为
- 后续如果 provider 再增加，可以从中策平滑演进到上策

换句话说，先把“多实现分文件”落地，再决定是否继续抽成更完整的 provider 框架。
