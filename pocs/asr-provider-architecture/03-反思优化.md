# ASR Provider 架构拆分 - 反思优化

> 创建时间：2026-05-04
> 选定方案：中策

## 边界情况

- **边界 1：不能把协议拆散**
  - 虽然要拆 provider 文件，但 `transcript_event / committed_text / draft_text / display_text / seq` 这套统一协议必须继续从一个通用模块产出。
  - 否则本地 provider 和阿里云 provider 又会重新长成两套协议语义。

- **边界 2：入口仍然只能有一个**
  - 外部前端只认 `/ws/asr`，不能因为内部拆分就暴露多个入口。
  - provider 选择必须留在入口层，而不是交给前端决定具体路径。

- **边界 3：日志不能拆没了**
  - 当前排障已经依赖 `worker-asr.log`。
  - 拆文件后日志必须仍然能保持统一前缀、统一落点、统一可读性。

- **边界 4：本地与云端实现差异很大**
  - 本地 ASR 是“本地缓存 + VAD + 识别”
  - 阿里云 ASR 是“音频转发 + 云端事件转换”
  - 因此不要过度追求内部流程完全一致，只需要统一入口与输出协议。

## 安全评估

- API Key 读取与使用应放到独立配置模块，避免分散在 provider 代码里
- provider 实现内部的异常应收敛为统一错误输出，避免把第三方原始异常直接泄漏给前端
- WebSocket 关闭逻辑需要统一封装，避免不同 provider 对断连处理不一致

## 影响分析

- **对前端影响**：理论上不应有接口变化，只要统一协议字段不变，前端无需同步大改
- **对后端影响**：`server.py` 会重构，但行为应保持一致
- **对排障影响**：短期需要适应新文件结构，长期排障会更清晰

## 性能与可维护性

- 目录拆分本身不会带来明显性能损耗
- 可维护性会明显提升，尤其是在：
  - 新增 provider
  - 单独修阿里云链路
  - 单独调本地 VAD
  - 单独测 transcript 协议

## 优化调整

在中策基础上做两点增强：

- **增强 1：先抽“通用协议层”，再拆 provider**
  - 先把 transcript 组装、日志输出、公共 merge 逻辑抽出来
  - 再拆 `local_provider.py` 和 `aliyun_provider.py`
  - 这样可以避免拆完文件后，公共代码仍然复制两份

- **增强 2：保留一个超薄 `server.py`**
  - `server.py` 只保留：
    - FastAPI app 初始化
    - startup
    - health
    - `/ws/asr`
    - provider 选择
  - 其他实现全部迁走

## 最终方案

最终采用“**单入口 + 通用协议层 + provider 分文件实现**”的方案：

- `server.py` 保留对外入口和最少量编排
- 通用协议与工具下沉到 `core/`
- 本地 / 阿里云各自进入 `providers/`
- provider 之间统一 `handle_ws()` 入口
- transcript 统一通过共享 emitter 输出

这样做的好处是：

- 当前可以先安全落地
- 不会一次重构过猛
- 后续可以继续平滑升级成完整的 provider 插件式架构
