# ASR Provider 架构拆分 - 需求分析

> 创建时间：2026-05-04

## 需求背景

当前 `resources/workers/asr/server.py` 同时承担了以下职责：

- Worker 启动与健康检查
- 模型加载与配置读取
- WebSocket 接入层
- 阿里云实时 ASR 适配
- 本地 ASR 识别与 VAD
- transcript 协议组装
- 日志与调试输出

随着 ASR 支持从单一实现扩展到多 provider（本地、阿里云，后续可能还有更多在线平台），单文件继续堆叠实现会带来几个明显问题：

- provider 逻辑耦合严重，阅读和排障成本高
- 统一协议虽然已建立，但实现仍散落在不同函数里
- 新增一个 provider 时，容易继续把判断分支堆进 `server.py`
- 单元测试和局部验证难做，改动风险高

## 核心目标

- 将 ASR Worker 拆成“统一接口 + 多实现”的结构
- 让 `server.py` 只保留入口编排，不再承载所有 provider 细节
- 把 transcript 协议、会话状态、日志能力抽成通用层
- 后续新增 provider 时，只需要新增实现文件并注册，而不是继续修改大块旧代码

## 约束条件

- 不能破坏当前前端已经依赖的统一 transcript 协议
- 不能影响当前 `/ws/asr` 的外部入口
- 不能在第一步拆分时同时大改前端逻辑
- 要兼容当前两类 provider：
  - 本地模型 ASR
  - 阿里云实时 ASR
- 要保留现有的日志与排障能力，避免“拆分后更难看日志”

## 涉及范围

- 模块：
  - ASR Worker
  - provider 选择与实例化
  - transcript 协议输出
  - WebSocket 会话生命周期
- 文件：
  - `resources/workers/asr/server.py`
  - 后续新增 `resources/workers/asr/providers/*`
  - 后续新增 `resources/workers/asr/core/*`
- 接口：
  - `/ws/asr`
  - transcript 统一协议字段
  - provider 内部抽象接口

## 需求本质

这次需求的本质不是“把大文件拆小”这么简单，而是要明确 ASR Worker 的三层边界：

- 入口层：接收外部连接，选择 provider，管理会话生命周期
- 通用层：统一 transcript 协议、通用日志、通用工具方法
- 实现层：不同 provider 的识别、VAD、事件转换逻辑

如果这三层不先分清，后面新增 provider 仍然会继续把逻辑堆回一个文件里。
