# ThreadWaker 过度设计简化 - 方案设计

> 创建时间：2026-04-28

## 问题拆解

本次简化包含 5 个独立问题：

1. **P1-1**：EventBus 自循环模式
2. **P1-2**：`tool-done` 死代码分支
3. **P1-3**：重复 ThreadStore 查询 + 多次动态导入
4. **P1-4**：runStatus 更新时机错误
5. **P1-5**：生产环境未接入

其中 P1-1 到 P1-4 是代码层面的问题，可以在一个文件内一次性解决。P1-5 是集成层面的问题，需要额外的一行调用。

## 上策：函数式简化（推荐）

**核心思路**：

将 `ThreadWaker` 从类 + EventBus 模式改为一个纯函数 `recoverPendingThreads()`，去掉所有架构开销，直接完成"扫描 → 恢复"的流程。

**具体设计**：

```typescript
// ThreadWaker.ts（简化后，约 55 行）

import { createLogger } from '@main/common/logger';
import { ThreadStore } from './ThreadStore';
import { threadExecutor } from '../ThreadExecutor';

const log = createLogger('thread-waker');

const RECOVERY_MESSAGE =
  `[System] The application was restarted while a task was in progress. ` +
  `The previous execution state has been preserved. ` +
  `Please describe what you'd like to do next, or ask me to continue the previous task.`;

/**
 * 系统启动时扫描未完成的 Thread 并提交恢复消息。
 *
 * 只恢复 runStatus 为 'running' 的 active thread。
 * 恢复通过 ThreadExecutor.submit() 走正常执行通道，内部由
 * ThreadExecutionFactory 自动装配 Agent 执行请求。
 */
export async function recoverPendingThreads(): Promise<void> {
  try {
    const threadStore = await ThreadStore.getInstance();
    const allThreads = await threadStore.listAsync();

    const pendingThreads = allThreads.filter((t) => t.status === 'active' && t.runStatus === 'running');

    if (pendingThreads.length === 0) {
      log.info('[ThreadWaker] No pending threads to recover on startup');
      return;
    }

    log.info(`[ThreadWaker] Found ${pendingThreads.length} pending thread(s) to recover`);

    for (const thread of pendingThreads) {
      try {
        const result = await threadExecutor.submit(thread.id, RECOVERY_MESSAGE);

        if (result.status === 'accepted') {
          log.info(`[ThreadWaker] Thread ${thread.id} resumed successfully`);
        } else {
          log.warn(`[ThreadWaker] Thread ${thread.id} is busy, skipping`);
        }
      } catch (error) {
        log.error(`[ThreadWaker] Failed to resume thread ${thread.id}:`, error);
      }
    }
  } catch (error) {
    log.error('[ThreadWaker] Startup recovery scan failed:', error);
  }
}
```

**改动范围**：

| 文件                              | 改动                                   |
| --------------------------------- | -------------------------------------- |
| `ThreadWaker.ts`                  | 整个文件重写，约 212 → 55 行           |
| `ThreadWaker.integration.test.ts` | 重写测试，去掉 EventBus mock           |
| 启动入口                          | 加一行 `await recoverPendingThreads()` |

**优势**：

- 去掉 EventBus 依赖，去掉类单例模式，去掉 start/stop 生命周期
- 代码量减少 75%
- ThreadStore 只查询一次，之后数据直接使用
- 不手动更新 runStatus，状态管理完全交给 ThreadExecutor
- 过滤条件明确：`status === 'active' && runStatus === 'running'`，一步到位，无需层层检查
- 纯函数风格：输入来自 ThreadStore，输出到 ThreadExecutor，无副作用
- 测试更简单：只需 mock `ThreadStore` 和 `threadExecutor`，不需要 EventBus、不需要访问私有方法

**劣势**：

- 失去了 `ThreadWakeEvent` 接口的类型约束（但该接口本身未被外部使用）
- 如果未来确实需要外部通过 EventBus 触发恢复（如 tool-done），需要重新引入——但根据当前架构分析，这个场景不应该走 EventBus

## 中策：最小裁剪（保留类结构）

**核心思路**：

保留 `ThreadWaker` 类，但：

1. `recoverOnStartup()` 内联调用 `handleRestartRecovery()`，不走 EventBus
2. 去掉 `tool-done` 分支
3. 合并 ThreadStore 查询
4. 去掉 runStatus 手动更新
5. 去掉 `start()/stop()`，启动入口直接调 `recoverOnStartup()`

**改动范围**：只改 `ThreadWaker.ts`，约 212 → 100 行

**优势**：

- 改动比上策更小
- 保留了类的结构，风格上与 `ThreadStore`、`AgentStore` 等一致

**劣势**：

- 仍然保留了不必要的类结构（单例、bound 函数绑定、start/stop 语义）
- 100 行实现一个约 20 行有效逻辑的功能，仍有浪费
- 测试仍需通过私有方法访问（或用 `as unknown as PrivateThreadWaker` 的类型体操）

## 下策：只修复导入路径（不简化）

**核心思路**：

只把 `import('../execution')` 改成 `import('../ThreadExecutor')`，其他不动。这是已经在做的最小修复。

**劣势**：

- EventBus 自循环、死代码、重复查询等问题全部保留
- 仍然没有接入生产启动流程
- 纯技术债累积

## 选定方案

**选择：上策（函数式简化）**

### 理由

1. 当前类的所有"架构"都是不必要的——EventBus 自循环、单例、生命周期管理——去掉它们不会损失任何功能
2. 代码量从 212 行降到 55 行，可读性和可维护性大幅提升
3. 函数式风格与 `ThreadExecutor` 的使用方式一致（`submit(threadId, message)` 就是函数调用）
4. 测试从"mock EventBus + 类型体操访问私有方法"变为"mock ThreadStore + mock threadExecutor"，更直接
5. 上策改动范围仍然很小（3 个文件），风险可控

### 具体实施步骤

#### 第一步：重写 ThreadWaker.ts

1. 删除 `ThreadWakeEvent` 接口（无外部引用）
2. 删除 `ThreadWaker` 类
3. 删除 EventBus 导入
4. 导出 `recoverPendingThreads()` 函数

#### 第二步：重写测试

1. 去掉 `vi.mock('../../ThreadExecutor')` 等 mock
2. 直接用 `vi.mock` mock `ThreadStore` 和 `threadExecutor`
3. 测试场景：
   - 无 pending threads
   - 有 running threads → submit 成功
   - submit 返回 busy
   - submit 抛出异常
   - ThreadStore.listAsync 失败

#### 第三步：接入启动流程

找到应用的 bootstrap 入口（`main.ts` 或 Gateway 初始化处），在 ThreadStore 就绪后调用：

```typescript
import { recoverPendingThreads } from '@main/agent/threads/ThreadWaker';

// 在应用启动完成、ThreadStore 可用后：
await recoverPendingThreads();
```

### 后续改进

本次简化完成后，ThreadWaker 模块已经足够精简，不需要进一步重构。如果未来有新的恢复触发源（如手动恢复、定时扫描），可以直接新增函数，不需要回到类 + EventBus 的模式。
