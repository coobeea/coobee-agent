# ThreadWaker 过度设计简化 - 需求分析

> 创建时间：2026-04-28

## 需求背景

在修复 `ThreadWaker.ts` 中 `import('../execution')` 路径错误（`threadExecutor` 实际定义在 `ThreadExecutor.ts` 而非 `execution/index.ts`）的过程中，对 `ThreadWaker.ts` 进行了完整代码审查，发现了多处过度设计和实际缺陷。

这个类当前有 **212 行代码**，但核心逻辑极其简单：系统启动时扫描未完成的 Thread，用 `threadExecutor.submit()` 提交一条恢复消息。然而现有实现存在以下问题：自循环事件总线、死代码分支、重复查询与重复过滤、无条件覆盖状态的潜在 bug、未使用的接口字段、误导性注释。

更关键的是：**`ThreadWaker` 在生产代码中从未被启动**——没有 bootstrap、main 入口或任何模块调用 `ThreadWaker.getInstance().start()` 或 `.recoverOnStartup()`，这两个方法只在测试文件中被调用。这意味着整个恢复机制目前是死代码。

## 核心目标

将 `ThreadWaker` 从 212 行过度设计的类简化为一个简洁的函数，去掉无意义的架构开销，只保留实际的恢复逻辑。

### 目标 1：消除自循环事件总线模式

**现状**：

```
recoverOnStartup()
  → eventBus.emit('thread:wake', ...)   // 发送事件
                                        // ↓ 同一个类
handleWake()                            // 监听同一个事件
  → resumeThread()
    → handleRestartRecovery()
```

`recoverOnStartup()` 通过 EventBus 发事件给**自己**的 `handleWake()`，这个 round-trip 没有任何解耦价值——生产者和消费者是同一个类。EventBus 的设计意图是解耦**不同模块**之间的通信，类内部的自循环纯属浪费。

**目标**：去掉 EventBus 自循环，改为直接方法调用。

### 目标 2：移除 `tool-done` 死代码

**现状**：

- `ThreadWakeEvent` 接口定义了 `reason: 'tool-done' | 'restart-recovery'`
- `resumeThread()` 中 `tool-done` 分支只打印一行 "Unhandled wake reason"，什么都不做
- 整个代码库没有任何地方 `emit('thread:wake', { reason: 'tool-done' })`

这是一个"为未来预留但从未实现"的功能。在当前架构中（`ThreadExecutionFactory` 已就位），工具审批应通过 RPC 方法直接调用 `threadExecutor.submit()`，不需要绕道 EventBus。

**目标**：移除 `tool-done` 分支和相关接口字段。

### 目标 3：消除重复的 ThreadStore 查询与重复的状态过滤

**现状**：

同一条 `restart-recovery` 调用链上，ThreadStore 被动态导入三次、查询了三次：

```
handleWake()              → await import('./ThreadStore') → store.get(threadId)   [第1次]
resumeThread()            → await import('./ThreadStore') → store.update(...)     [第2次]
handleRestartRecovery()   → await import('./ThreadStore') → store.get(threadId)   [第3次，重复查询]
```

其中 `handleWake()` 拿到的 `threadDef` 完全可以直接传给下游，不需要 `handleRestartRecovery()` 再查一次。

**不仅如此，状态过滤也是重复的**：

- `recoverOnStartup()` 第 191 行过滤了 `idle` 和 `completed`
- `handleWake()` 第 97 行**又过滤了一遍** `idle` 和 `completed`（同一批数据）
- `handleRestartRecovery()` 第 143 行**第三次过滤**：只放行 `running` 和旧的 `tool-pending`

三层过滤散落在三个方法里，且逻辑不一致——如果未来增加新的 runStatus（如 `paused`），谁知道该在哪一层加条件？

**目标**：一次查询，一次过滤，结果向下传递，不再重复。

### 目标 4：修正 `resumeThread()` 无条件覆盖 runStatus 的潜在 bug

**现状**（`resumeThread()` 第 111-121 行）：

```typescript
private async resumeThread(threadId: string, event: ThreadWakeEvent): Promise<void> {
    if (event.reason === 'restart-recovery') {
        await this.handleRestartRecovery(threadId);  // 可能提前 return（状态不匹配）
    } else {
        log.info(`Unhandled wake reason: ${event.reason}`);
    }
    // ↓ 无论上面发生了什么，无条件把状态改成 'running'
    await threadStore.update(threadId, { runStatus: 'running' });
}
```

这里有两个问题：

**问题 A — 无条件覆盖**：第 120 行的 `update({ runStatus: 'running' })` 是**无条件执行**的。即使 `handleRestartRecovery()` 因为状态不匹配（比如 thread 是 `paused`）而提前 return 了，即使 reason 是 `tool-done` 只打了一行日志，这里都会强行把 runStatus 改成 `running`。这意味着一个 `paused` 状态的 thread 会在恢复流程中被错误地标记为 `running`。

**问题 B — 冗余写**：即使 `handleRestartRecovery()` 成功调用了 `threadExecutor.submit()`，执行器内部也会通过 ThreadStore 更新状态。这里是冗余写入，极端情况下可能与执行器产生竞态。

**目标**：删除 `resumeThread()` 中无条件的 `update({ runStatus: 'running' })`，状态管理完全交给执行器和 ThreadStore。

### 目标 5：清理 `ThreadWakeEvent` 接口中从未被使用的字段

**现状**：

```typescript
export interface ThreadWakeEvent {
  threadId: string;
  reason: 'tool-done' | 'restart-recovery';
  toolResult?: string; // ← 从未被读取
  approvalDecision?: string; // ← 从未被读取
  toolName?: string; // ← 从未被读取
  toolParams?: Record<string, unknown>; // ← 从未被读取
}
```

`handleWake()` 第 84 行只解构了 `threadId` 和 `reason`，`approvalDecision`、`toolName`、`toolParams`、`toolResult` 四个字段从未被任何代码读取。这些是为"工具审批后通过 EventBus 唤醒 Thread"场景预留的，但这个场景从未实现（与目标 2 的 `tool-done` 属于同一套未实现的设计）。

**目标**：删除 `ThreadWakeEvent` 接口，恢复流程不再需要事件数据结构。

### 目标 6：修正误导性注释

**现状**（`handleRestartRecovery()` 第 126-128 行注释）：

```typescript
/**
 * 系统重启后恢复
 *
 * 支持两种恢复模式：
 *   1. 普通 Agent Thread：通知用户中断了什么
 *   2. Discussion Thread：自动恢复讨论协调
 */
```

代码中只有第 1 种模式的实现，第 2 种"Discussion Thread 自动恢复讨论协调"从未被实现。注释声称的功能与实际代码不符，属于误导性文档。

**目标**：简化后不再需要这段注释，因为恢复逻辑是统一的——只要是 `running` 的 active thread 就走同一套恢复流程。

### 目标 7：接入生产启动流程

**现状**：`start()` 和 `recoverOnStartup()` 没有任何生产代码调用。

**目标**：将恢复逻辑接入应用的 bootstrap 流程（例如 `main.ts` 或 Gateway 启动时），让它在生产环境中真正生效。

## 约束条件

### 技术约束

1. **不动外部接口**：`threadExecutor.submit(threadId, message)` 的调用签名不变
2. **测试兼容**：简化后测试文件需要同步更新，但测试覆盖的核心场景（Thread 不存在、Agent 不存在、submit 成功/失败）应保持
3. **不引入新依赖**：不创建新的抽象层或工厂

### 代码约束

- 保持日志输出，便于问题排查
- 保持 TypeScript 严格类型，不使用 `any`

## 涉及范围

### 模块

- `src/main/agent/threads/ThreadWaker.ts` — 主要改造目标，大幅缩减
- `src/main/agent/threads/__tests__/ThreadWaker.integration.test.ts` — 同步更新测试
- 应用启动入口（`main.ts` 或 Gateway 初始化处）— 接入 `recoverOnStartup()` 调用

### 不涉及的模块

- `ThreadExecutor.ts` — 接口不变
- `ThreadExecutionFactory.ts` — 不修改
- `ChatRoutes.ts` / `ChatMethods.ts` — 不修改
- `ThreadStore.ts` — 不修改

## 非目标

以下内容不在本次简化范围内：

1. 不修改 ThreadExecutor 或 AgentExecutor 的内部逻辑
2. 不改变恢复消息的内容（系统提示文案保持不变）
3. 不增加新的恢复策略（如 Discussion Thread 的自动协调，注释中提到但从未实现）
4. 不处理多个 Thread 并发恢复的调度优化

## 验收标准

- [ ] 代码行数从 212 行降到约 60 行以内
- [ ] 去掉 EventBus 自循环（不再监听 `thread:wake`，不再 `emit` 给自己）
- [ ] 去掉 `tool-done` 死代码
- [ ] ThreadStore 只查询一次，一次过滤
- [ ] 不手动更新 runStatus
- [ ] 删除 `ThreadWakeEvent` 接口及其未使用字段
- [ ] `pnpm typecheck` 通过
- [ ] 现有测试更新后通过（4 个核心场景）
- [ ] 恢复逻辑在生产启动流程中被调用

## 风险评估

**低风险**：

- ThreadWaker 当前是死代码（生产环境从未启动），简化不会影响现有功能
- 改动仅限一个文件 + 测试文件 + 一行启动调用
- 核心逻辑不变（扫描 pending threads → submit 恢复消息）

**需要注意**：

- 测试文件需要较大幅度的重写（不再 mock EventBus、不再通过私有方法访问）
- 接入启动流程时需要注意初始化顺序（ThreadStore 必须先就绪）
