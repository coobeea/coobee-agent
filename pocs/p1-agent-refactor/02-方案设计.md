# Agent 模块 P1 阶段重构 - 方案设计

> 创建时间：2026-04-22
> 状态：设计中

## 一、方案概览

针对 P1 阶段的 5 个问题 + 1 个 P0 遗留问题，我们给出三种不同层次的方案。

## 二、上策：完整重构（最优方案）

### 核心思路

**一次性解决所有 P1 问题，彻底消除职责重叠和架构漂移。**

### 改动清单

#### 1. 新增 `AgentContextResolver`（解决 P1-1）

**位置**：`src/main/agent/context/AgentContextResolver.ts`

**职责**：统一解析运行期上下文，包括：
- `agentHomePath`
- `dataDirectory`
- `workspacePath`
- `effectiveModel`
- `sessionDir`

**接口设计**：

```typescript
interface AgentContext {
  agentId: string;
  agentHomePath: string;
  dataDirectory: string;
  workspacePath: string | undefined;
  effectiveModel: string | undefined;
  sessionDir: string;
}

class AgentContextResolver {
  async resolve(params: {
    agentId: string;
    sessionId: string;
    threadId?: string;
    workspace?: string;
    modelOverride?: string;
  }): Promise<AgentContext>
}
```

**改动影响**：
- `AgentStore.create()` 不再初始化路径，只存定义
- `ThreadStore.create()` 不再调用 `ensureAgentDataDirectory()`
- `AgentEnvInjector.injectEnv()` 调用 `resolver.resolve()` 获取上下文

---

#### 2. 新增 `ThreadExecutionFactory`（解决 P0-2 遗留）

**位置**：`src/main/agent/execution/ThreadExecutionFactory.ts`

**职责**：统一 Thread 执行的 Builder 配置逻辑。

**接口设计**：

```typescript
class ThreadExecutionFactory {
  async createBuilder(params: {
    threadId: string;
    sessionMode?: 'file' | 'memory';
  }): Promise<PiMonoBuilder>
}
```

**改动影响**：
- `ChatRoutes.sendMessage()` 调用 `factory.createBuilder()`
- `ThreadWaker.submitResumeMessage()` 调用 `factory.createBuilder()`
- 删除两处重复的配置代码（约 30 行）

---

#### 3. 新增 `PromptAssemblyService`（解决 P1-4）

**位置**：`src/main/agent/prompt/PromptAssemblyService.ts`

**职责**：统一 Prompt 拼装逻辑，提供预算统计。

**接口设计**：

```typescript
interface PromptBlock {
  source: string; // 'instructions' | 'agent_home' | 'skills' | ...
  content: string;
  tokens: number;
}

class PromptAssemblyService {
  async assemble(context: AgentContext): Promise<{
    blocks: PromptBlock[];
    totalTokens: number;
    warnings: string[];
  }>
}
```

**改动影响**：
- `AgentEnvInjector` 不再自己拼 `appendInstructions`
- `PiMonoAgentRuntime` 不再双重注入技能信息
- 所有 Prompt 来源可追溯

---

#### 4. 清理 `AgentEventWriter`（解决 P1-2）

**改动方式**：

- **选项 A**：完全删除 `AgentEventWriter`，Extension 场景也改用 EventBus
- **选项 B**：保留 `AgentEventWriter` 作为 EventBus 的适配层，明确标注用途

**推荐**：选项 B，保持向后兼容。

**改动影响**：
- 更新 `AgentExecutor.ts` 顶部注释
- 更新架构文档，明确唯一事件链路
- 在 `AgentEventWriter` 加注释说明其为适配层

---

#### 5. 统一 Runtime 事件模型（解决 P1-3）

**改动方式**：

- OpenAI Runtime 不再直接调用 `streamEmitter.forward()`
- 所有业务事件（`agent_updated`, `tool:delta`）改为 `yield StreamChunk`
- Executor 统一转发

**改动影响**：
- `OpenAIAgentRuntime.ts` 修改 `agent_updated` 和工具增量输出逻辑
- 可能需要调整 `StreamChunk` 类型定义
- 需要测试 SSE 和 EventBus 的一致性

---

#### 6. 修正生命周期 priority（解决 P1-5）

**改动方式**：

```typescript
// ReadyGatewayHook.ts
export const priority = 45; // 改为 45

// ReadyAgentSystemHook.ts
export const priority = 50; // 保持 50
```

**改动影响**：
- 确保 Gateway 先于 Agent System 初始化
- 更新注释，代码和注释保持一致
- 增加集成测试验证初始化顺序

---

### 优势

- ✅ 彻底解决所有 P1 问题
- ✅ 架构最优，职责清晰
- ✅ 长远收益高，后续维护成本低
- ✅ Prompt 拼装可追溯，便于优化 token 成本

### 劣势

- ❌ 改动范围大（约 10+ 个文件）
- ❌ 实施周期长（预计 3-5 天）
- ❌ 测试工作量大
- ❌ 需要同步更新大量文档

### 风险评估

- **破坏现有功能**：中等（需要完整回归测试）
- **难以完成**：中等（可分多个 PR 提交）
- **团队协作冲突**：低（改动集中在 agent 模块）

---

## 三、中策：分批重构（平衡方案）⭐ 推荐

### 核心思路

**分两批处理：优先解决影响面大且风险低的问题。**

### 批次划分

#### 批次 1：路径和配置统一（优先级高）

**解决问题**：P1-1, P0-2 遗留, P1-5

**改动清单**：

1. **新增 `AgentContextResolver`**（同上策）
   - 统一路径解析逻辑
   - 重构 `AgentStore`, `ThreadStore`, `AgentEnvInjector`

2. **新增 `ThreadExecutionFactory`**（同上策）
   - 消除 ChatRoutes 和 ThreadWaker 的代码重复
   - 统一 Builder 配置

3. **修正生命周期 priority**（同上策）
   - Gateway priority 改为 45
   - 增加测试验证

**预计工作量**：1-2 天

**风险**：低（逻辑清晰，影响面可控）

---

#### 批次 2：事件和 Prompt 统一（后续优化）

**解决问题**：P1-2, P1-3, P1-4

**改动清单**：

1. **清理 `AgentEventWriter`**
   - 改为 EventBus 适配层
   - 更新文档和注释

2. **统一 Runtime 事件模型**
   - OpenAI Runtime 改用 yield 方式
   - 测试 SSE 和 EventBus 一致性

3. **新增 `PromptAssemblyService`**（可选）
   - 统一 Prompt 拼装
   - 提供 token 预算统计

**预计工作量**：2-3 天

**风险**：中等（涉及事件流和 Runtime 内部逻辑）

---

### 优势

- ✅ 风险可控，渐进式重构
- ✅ 优先解决影响最大的问题
- ✅ 可以分两个 PR 提交，便于 review
- ✅ 如果批次 1 出问题，批次 2 可以延后

### 劣势

- ⚠️ 需要两轮开发周期
- ⚠️ 批次 1 完成后仍有技术债（P1-2, P1-3, P1-4）

### 风险评估

- **破坏现有功能**：低（批次 1 改动集中且清晰）
- **难以完成**：低（分批降低复杂度）
- **团队协作冲突**：低

## 六、推荐方案

### ⭐ 推荐：中策（分批重构）

**理由**：

1. **风险可控**：批次 1 的改动都是逻辑清晰、影响面可控的
2. **优先级合理**：先解决影响面最大的问题（路径漂移、代码重复、生命周期竞态）
3. **便于 review**：两个 PR 分别处理，review 压力小
4. **灵活性高**：如果批次 1 出问题，批次 2 可以延后或调整

### 实施建议

**批次 1（立即开始）**：
- Week 1: 实现 `AgentContextResolver` 和 `ThreadExecutionFactory`
- Week 1: 修正生命周期 priority
- Week 1: 运行完整测试，提交 PR

**批次 2（批次 1 合并后）**：
- Week 2: 清理 `AgentEventWriter`，更新文档
- Week 2: 统一 Runtime 事件模型
- Week 3: （可选）实现 `PromptAssemblyService`
- Week 3: 运行完整测试，提交 PR

### 回退策略

如果批次 1 遇到阻塞问题，可以：
- 降级到「下策」，只完成 `ThreadExecutionFactory`
- 或者暂停批次 1，先做批次 2 中风险更低的部分（清理文档、修正 priority）
