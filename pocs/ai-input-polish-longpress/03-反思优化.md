# 输入框 Ctrl 长按 AI 润色 - 反思优化

## 旧实现可吸收点

- Renderless 组件思路很好：AI 能力通过 slot props 暴露，不强占业务 UI。
- 指令思路很好：把生成能力绑定到任意元素，适合“输入框增强”。
- 长按 Ctrl 的等待态很好：用户按下后能看到“即将触发”的反馈，而不是黑箱等待。
- 生成中浮层预览很好：即使最终自动回填，也让用户知道系统正在处理。
- 生成完成后触发原生 `input` 事件是必要的，可以让 Vue `v-model` 同步更新。

## 旧实现不应照搬点

- 旧项目依赖 `services/ai/agents/*` 固定 agent service，不适合当前项目。
- `AiForm.vue` 强依赖 `.input` CSS 类和表单验证上下文，通用性不够。
- 旧项目对 JSON 解析和表单填充做得较重，本需求只需要纯文本润色。
- 旧项目的图标体系是 MDI，当前项目应优先使用 Carbon 图标。

## 当前项目关键约束

- 前端不能直接调用主进程 `ThreadlessExecutor`，需要通过 Gateway/RPC 或 HTTP 路由。
- 前端可以封装 `useThreadExecutor` / `useThreadlessExecutor`，让业务侧不用直接依赖具体 RPC 方法名。
- 当前 `components/common/AIGenerate.vue` 的 `quickChatStream` 是占位，不能直接依赖。
- 默认 agent 应使用 `app-copilot`，默认模型由 Agent/全局配置解析。
- 润色 prompt 必须强约束“只返回润色后的文本”，避免解释性输出污染输入框。
- `threadless` 调用不应写入 `chatStore`，也不应创建持久化 Thread，否则会污染正式会话历史。
- `instructions` 应作为独立参数设计；短期可以在后端拼入执行请求，长期不建议让每个前端业务组件手工拼接系统约束。
- Threadless 场景本质是一次请求、一次响应，应选择 HTTP，避免引入 WebSocket RPC 带来的连接状态依赖和请求 id 匹配复杂度。

## 通信协议选型（HTTP vs WebSocket RPC）

- **选定结论**：`useThreadlessExecutor` 使用 HTTP，不走 WebSocket RPC。
- **核心理由**：
  - Threadless 调用是一次请求、一次响应，不需要监听任何 `stream:*` 事件。
  - WS RPC 主要用于 Chat 流式场景，一次 `sendMessage` 会在服务端产生 reasoning/text/tool-call/tool-result/usage/done 等多类事件，需要长连接通道持续推回并和 `chatStore.handleStreamMessage` 挂钩。
  - Threadless 没有这些需求，如果硬走 RPC：前端要先建立/依赖 WS 连接（错峰触发时需要等待或降级）；还要发明一个同步 RPC 的请求 id 匹配机制，本质是在 WS 上模拟一次 HTTP，业务层拿不到额外收益。
  - 项目已有统一 HTTP 路由体系（[routes/README.md](file:///Users/lifeng/git/git-coobee/coobee-agent/src/main/routes/README.md)）：自动扫描 `*Routes.ts`、统一响应格式 `{ success, data }`、前缀 `/gateway`、端口 `8765`；前端 [renderer/src/api](file:///Users/lifeng/git/git-coobee/coobee-agent/src/renderer/src/api) 已有 `ApiResponse<T>` 和 `apiClient` 的封装范式，复用成本低。
  - `ThreadlessExecutor.run` 本身已在服务端把流式 chunk 聚合成字符串，天然与同步 HTTP 匹配。
- **覆盖面**：本次只影响 `useThreadlessExecutor` 通道选型；`useThreadExecutor`（Chat 场景）仍走 WS RPC，不受影响。
- **后续扩展**：若需要流式预览，新增 `POST /gateway/threadless/run/stream`（SSE），仍在 HTTP 通道内解决，不必回头挂 WS。
- **取消机制**：前端使用 `AbortController` + `fetch` 的 `signal`，服务端监听 `ctx.req.on('close')` 下发底层 `AbortSignal`，复用现有“AbortSignal 全链路监听”能力。

## Executor 封装边界

- `useThreadExecutor` 只负责已有会话：创建 Thread、发送消息、停止消息。它不替代现有 `stream:*` 事件消费链路；通信协议仍为 WebSocket RPC。
- `useThreadlessExecutor` 只负责无会话请求：润色、摘要、翻译、字段生成等轻量 AI 调用都应走这里；通信协议为 HTTP（`apiClient.post`），不依赖 WS 连接状态。
- `useAITextPolish` 属于 preset 层，只描述“怎么润色一句话”，不关心底层是 HTTP、未来的 SSE 还是 WS。
- 指令 `v-ai-polish` 属于交互层，只处理长按、浮层、回填、事件派发，不直接拼接模型请求。

## 交互边界

- 长按时长建议默认 800ms 到 1200ms，可配置；旧项目 2000ms 稍慢。
- Ctrl/Control 触发应只在输入框聚焦时有效。
- 生成中再次触发应忽略或取消前一次，推荐忽略并显示处理中状态。
- 空内容不触发润色，可以提示“先输入内容”。
- 结果为空或与原文一致时不破坏原输入。
- 对 `input`/`textarea` 应保留光标位置；对 `contenteditable` 和 TipTap 需要单独适配。

## Prompt 建议

默认提示词应该简短、稳定、可覆盖：

```text
请润色下面这句话，让表达更自然、清晰、简洁。保持原意、保留原语言，不要扩写成多段，不要添加解释，不要使用 Markdown，只返回润色后的句子。

原句：
{{text}}
```

可扩展变量：

- `text`：当前输入内容。
- `label`：字段标签。
- `placeholder`：输入框占位符。
- `context`：业务组件传入的额外上下文。
