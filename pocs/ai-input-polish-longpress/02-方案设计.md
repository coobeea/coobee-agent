# 输入框 Ctrl 长按 AI 润色 - 方案设计

## 上策：建立通用 AI 生成基础设施

### 核心思路

建立完整的通用 AI 生成层：

- 后端新增 HTTP 路由 `POST /gateway/ai/generate`（同步）与后续可选的 `POST /gateway/ai/generate/stream`（SSE），底层使用 `ThreadlessExecutor`。
- 前端新增 `useAIGenerate` 组合式 API，统一处理状态、取消、错误、流式文本。
- 前端新增 `v-ai-generate` 指令，支持点击、快捷键、长按等触发模式。
- 前端新增轻量 `AIGenerate.vue` renderless 组件，保留旧项目 slot props 思路。
- 输入框润色只是其中一个 preset：`preset: 'polish-one-line'`。

### 优点

- 长期复用性最好，后续总结、翻译、扩写、纠错都能共用。
- 能自然吸收旧项目 renderless 组件、指令和弹层管理的优点。
- 可以给 ChatInput、AgentEditor、设置页等不同场景统一接入。

### 缺点

- 需要一次性设计较完整的 API 和事件模型。
- 如果当前只要“一句话润色”，实现成本偏高。

## 中策：先做输入框润色专用通路，再保留通用扩展口

### 核心思路

先实现一个小而稳的专用闭环：

- 前端先在 `src/renderer/src/composables` 中封装一套与后端 Executor 对齐的方法：
  - `useThreadExecutor`：面向已有会话，封装 `chat.createThread`、`chat.sendMessage`、`chat.abortMessage`。已有会话的流式事件仍由 WebSocket 通道 + `stream:*` 事件 + `chatStore.handleStreamMessage` 承接，本 composable 不重复承接。
  - `useThreadlessExecutor`：面向无会话、一次性、同步的轻量调用，底层走 **HTTP**（非 WebSocket RPC），调用后端新增的 `POST /gateway/threadless/run`，符合 `ApiResponse<T>` 统一契约。
  - 上层 AI 能力不直接调用 `fetch`/`apiClient`，而是调用这些 composable。
- 后端新增 Threadless HTTP 路由（`src/main/routes/ThreadlessRoutes.ts`）：
  - 同步端点：`POST /gateway/threadless/run`，返回最终文本。
  - 流式端点（可选，后续补）：`POST /gateway/threadless/run/stream`，采用 SSE，按需支持 `text:delta` 实时预览。
  - 入参尽量贴近后端 `ThreadlessExecutor.runMessage`：`agentId`、`message`、`runtimeType?`、`mode?`、`lightweight?`、`maxTurns?`、`sessionId?`。
  - 为了支持“传递指令等其他参数”，后端需要新增可选扩展字段：`instructions?`、`modelOverride?`、`promptVars?`、`metadata?`。
  - 初版可先只支持 `instructions?` 作为本次请求的附加系统约束；如果要真正覆盖系统指令，需要同步扩展 `ThreadlessExecutor.createRequest`。
  - 响应：`ApiResponse<ThreadlessRunRespVO>`，成功时 `{ success: true, data: { text, sessionId?, usage? } }`，失败时 `{ success: false, error }`。
  - 取消：监听 `ctx.req.on('close')`，把底层 `AgentExecutor` 的 `AbortSignal` 一并断开，避免模型空跑。
- 前端新增 `useAITextPolish`：
  - 管理 `idle/pending/generating/success/error` 状态。
  - 负责构造“一句话润色” prompt。
  - 通过 `useThreadlessExecutor().run(...)` 调用默认 `app-copilot`。
  - 支持取消标记和防重复触发。
- 前端新增 `v-ai-polish` 指令：
  - 绑定到输入框或输入容器。
  - 聚焦后长按 Ctrl/Control 触发。
  - 显示小型浮层：等待触发、生成中、失败、完成。
  - 完成后回填输入框并派发 `input`/`change` 事件。

### 前端 Executor Composable 设计

新增的前端方法放在 `src/renderer/src/composables`，命名和职责尽量贴近后端 Executor：

#### `useThreadExecutor`

面向“已有会话”的执行入口，本质是对 `chat.*` RPC 做类型化封装。它不直接处理流式消息拼接，流式结果仍然由现有 `stream:*` 事件和 `chatStore.handleStreamMessage` 承接。

```ts
export interface CreateThreadOptions {
  title?: string;
  agentId?: string;
  overrideModel?: string;
  runtimeType?: 'pi-mono' | 'openai' | 'claude';
  enableThinking?: boolean;
  asrEnabled?: boolean;
  ttsEnabled?: boolean;
}

export interface SendThreadMessageOptions {
  threadId: string;
  message: string;
  runtimeType?: 'pi-mono' | 'openai' | 'claude';
}

export function useThreadExecutor() {
  return {
    createThread(options?: CreateThreadOptions): Promise<ThreadDefinition>;
    sendMessage(options: SendThreadMessageOptions): Promise<{ success: true }>;
    abortMessage(threadId: string): Promise<{ success: boolean; aborted: boolean }>;
  };
}
```

初版实现映射：

- `createThread` -> `chat.createThread`
- `sendMessage` -> `chat.sendMessage`
- `abortMessage` -> `chat.abortMessage`

#### `useThreadlessExecutor`

面向“无会话、轻量、一次性”的执行入口，用来承接输入框润色、摘要、翻译、字段生成等能力。它不写入 `chatStore`，也不创建持久化 Thread。**通信协议使用 HTTP（非 WebSocket RPC）**——因为该场景本质是一次请求、一次响应，无需监听任何 `stream:*` 事件，走 HTTP 可以直接得到结果，同时避免依赖 WS 连接状态。

```ts
export interface ThreadlessRunOptions {
  agentId?: string;
  message: string;
  instructions?: string;
  runtimeType?: 'pi-mono' | 'openai' | 'claude';
  mode?: 'chat' | 'agent';
  lightweight?: boolean;
  maxTurns?: number;
  sessionId?: string;
  modelOverride?: string;
  promptVars?: Record<string, unknown>;
  metadata?: Record<string, unknown>;
}

export interface ThreadlessRunResult {
  text: string;
  sessionId?: string;
  usage?: unknown;
}

export function useThreadlessExecutor() {
  return {
    run(options: ThreadlessRunOptions): Promise<ThreadlessRunResult>;
  };
}
```

默认参数建议：

- `agentId = 'app-copilot'`
- `mode = 'chat'`
- `lightweight = true`
- `maxTurns = 1`

初版实现映射：

- `run` -> `POST /gateway/threadless/run`（通过 `apiClient.post` 调用，返回 `ApiResponse<ThreadlessRunRespVO>`）
- 后续如果需要边生成边展示，再补 `stream` -> `POST /gateway/threadless/run/stream`（SSE）
- 请求支持 `AbortController`，前端取消时自动调用 `signal.abort()`，服务端通过 `ctx.req.on('close')` 感知并终止底层执行。

#### `useAITextPolish`

`useAITextPolish` 是上层 preset，不直接调用 `useGateway`：

1. 根据原文、字段标签、占位符、业务上下文构造 `message`。
2. 把“一句话润色”的行为约束放入 `instructions`。
3. 调用 `useThreadlessExecutor().run(...)`。
4. 管理 `idle/pending/generating/success/error` 状态和防重复触发。

这样以后做“摘要”“翻译”“改写”“生成字段值”时，只需要新增 preset composable 或配置，不需要每个功能重新设计一套请求链路。

### 优点

- 实现成本适中，直接满足当前需求。
- 边界清晰，不污染现有 Chat 对话流和 chatStore。
- 前端调用入口与后端 `ThreadExecutor` / `ThreadlessExecutor` 对齐，后续更容易维护。
- `instructions`、`modelOverride`、`metadata` 等扩展参数有明确归属，不需要在业务组件里硬拼 prompt。
- HTTP 协议不依赖 WS 连接状态，长按 Ctrl 触发时即使 WS 尚未建立也能立即请求，与现有 `routes/README.md` 的自动扫描机制天然对齐。
- 后续可以在 `useThreadlessExecutor` 上继续扩展 `stream`（SSE），让通用 AI 能力逐步支持流式体验，仍走 HTTP 通道。

### 缺点

- 初版不是完整通用生成平台。
- `POST /gateway/threadless/run` 需要新增后端 HTTP 路由。
- `instructions`、`modelOverride` 等字段如果要真正影响底层执行，需要同步扩展 `ThreadlessExecutor.createRequest`。
- 流式预览若走同步 HTTP 只返回最终文本，体验弱于旧项目；后续可补 SSE 路由。

## 下策：只在某个输入组件内硬编码 Ctrl 长按润色

### 核心思路

直接在目标输入组件内监听 Ctrl 长按，调用一个后端接口回填。

### 优点

- 最快。

### 缺点

- 复用性差。
- 后续每个输入框都要重复接入。
- 不符合用户希望“通用组件/通用能力”的方向。

## 选定方案

推荐中策，把接口边界从专用 `ai.polishText` 调整为通用 `threadless.run` HTTP 路由 + 前端 Executor composables。

具体落地顺序：

1. 先在 `src/shared/api/threadless-types.ts` 定义 `ThreadlessRunReqVO` / `ThreadlessRunRespVO`，在 `src/renderer/src/api/threadless.ts` 基于 `apiClient.post` 封装 HTTP 调用。
2. 后端新增 `src/main/routes/ThreadlessRoutes.ts`，暴露 `POST /gateway/threadless/run`，内部复用 `ThreadlessExecutor.runMessage`，同时扩展 `ThreadlessExecutionOptions` 支持 `instructions?` / `modelOverride?`。
3. 前端 `src/renderer/src/composables` 设计 `useThreadExecutor`（仍走 `useGateway` RPC，因为 Chat 是流式场景）与 `useThreadlessExecutor`（走 HTTP `apiClient`）。
4. `useAITextPolish` 作为“一句话润色” preset 调用 `useThreadlessExecutor().run(...)`，不关心底层是 HTTP 还是未来的 SSE。
5. `v-ai-polish` 只负责长按交互、浮层反馈和回填，不关心底层通道。

这个方案既能满足当前输入框润色，也能把前端发起 Agent 请求的方式沉淀成一套可复用的基础能力。
