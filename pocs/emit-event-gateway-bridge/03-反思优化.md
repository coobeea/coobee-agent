# emit_event 后端到前端事件链路缺失 - 反思优化

> 创建时间：2026-04-29
> 最近更新：2026-04-29

## 方案复盘

最终方案调整为：**固定 `agent:message` 通道 + `action` 分发 + `payload.text/data` 两字段结构**。

这个方案比“每个 action 一个 Gateway 顶层事件”更适合扩展，因为 Gateway、Publisher、gatewaySetup 不会随着 action 增加而持续膨胀。

## 已确认的代码事实

### 1. Publisher 是自动扫描，不需要手动 import

`Gateway.discoverEventPublishers()` 会扫描 `src/main/publishers/**/*Publisher.ts`，支持三种形式：

- `export default string[]`
- `export default Record<string, unknown>`
- 导出函数名以 `init` 开头

因此 AgentMessagePublisher 最适合使用数组形式：

```ts
export default [AgentEventTypes.MESSAGE];
```

原方案中 `registerPublisher()` 的写法不会被现有扫描逻辑识别，已经调整。

### 2. 前端已有 Gateway 到 EventBus 的桥接分层

当前 renderer 的事件流是：

```text
GatewayClient.on(...)
  -> gatewaySetup.ts
    -> eventBus.emit(...)
      -> eventbus/event_handles/*EventsHandle.ts
```

所以 Agent Message 也应该走这个结构。直接在任意组件中 `useGateway().on(...)` 会绕过现有分层，不利于后续统一维护。

### 3. `useOpenFiles` 已具备 open-file / open-preview 能力

前端已有：

- `useOpenFiles().openFile(filePath)`
- `useOpenFiles().openUrl(url, title)`

因此 `open-file` 和 `open-preview` 不需要新建工作台能力，只需要事件 handler 调用已有 composable。

## 风险与修正

### 风险一：过多顶层 Agent 事件会导致 Gateway 类型膨胀

如果使用：

- `agent:open-preview`
- `agent:open-file`
- `agent:notify`
- `agent:xxx`

后续每加一个 action，就要同步改 shared Gateway 类型、Publisher、gatewaySetup、前端 EventBus 类型。这和 `thread:message` 的稳定通道思路不一致。

修正：

- 外层固定 `agent:message`
- action 放入 message 内部
- Publisher 和 gatewaySetup 只关心 `agent:message`

### 风险二：payload 统一后静态类型会变弱

统一 payload 为：

```ts
{
  text?: string;
  data?: Record<string, unknown>;
}
```

这会让 TypeScript 无法直接表达 “open-preview 必须有 data.url”。但这个取舍是可接受的，因为它换来了消息格式稳定。

修正：

- `normalizeAgentMessage` 必须按 action 做运行时校验
- 前端 handler 也要对关键字段做防御性检查

### 风险三：工具参数名 `event` 与内部字段 `action` 容易混淆

当前工具已经使用 `event` 参数。为了减少对 Agent 的破坏，可以先保留 `event` 字段，但文档和内部类型都明确它的语义是 action。

修正：

- 工具描述中写明：`event` is the action name
- 内部构建的 `AgentMessage.action = params.event`
- 后续如果要重命名为 `action`，可以单独做兼容迁移

### 风险四：过早支持任意 action 会扩大前端攻击面

虽然 `AgentMessage.action` 类型上可以是 string，但当前第一阶段只执行三种内置 action。若直接允许任意 action 执行，会导致：

- 前端事件处理不可控
- 难以审计
- 后续权限控制困难

修正：

- `normalizeAgentMessage` 第一阶段只允许三种内置 action
- 未知 action 返回工具失败
- 后续新增 action 时，先补 action 说明和 handler，再放开校验

### 风险五：测试如果只测工具仍会漏掉桥接问题

当前问题就是工具测试通过，但端到端链路断了。因此新增测试必须覆盖至少三层：

- 工具发射的 EventBus 事件名为 `agent:message`
- Publisher 默认导出 `[AgentEventTypes.MESSAGE]`
- 前端 event handler 对 UI 能力的调用

## 最终调整

相对上一版方案，最终调整为：

1. 不再使用 `agent:open-preview`、`agent:open-file`、`agent:notify` 作为 Gateway 顶层事件。
2. 统一使用 `agent:message`。
3. message 内部通过 `action` 分发。
4. `payload` 统一为 `{ text?: string; data?: Record<string, unknown> }`。
5. 当前只允许三种内置 action：`notify`、`open-preview`、`open-file`。
6. Publisher 使用 `export default [AgentEventTypes.MESSAGE]`。
7. `gatewaySetup.ts` 只桥接 `agent:message`。
8. `agentEventsHandle.ts` 按 action 执行 UI 行为。
