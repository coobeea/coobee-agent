# emit_event 后端→前端事件链路缺失 - 反思优化

> 创建时间：2026-04-29

## 设计反思

### 1. 为什么 Publisher 模式没有被复用？

现有 Gateway 的 EventBridge 机制（Publisher 目录）已经成熟：`StreamPublisher.ts` 和 `ThreadPublisher.ts` 都在正常工作。`emit_event` 工具是后来添加的，但没有同步创建对应的 Publisher。

推测原因：
- 工具开发和 Gateway 桥接由不同的人 / 不同时间段完成
- 工具开发时只关注了工具本身的正确性（参数 schema、执行逻辑），遗漏了端到端集成
- 测试只验证了 EventBus 发射（`emit-event.test.ts`），没有验证前端是否能收到

**教训**：类似 emit_event 这样的"通信类"工具，端到端测试（EventBus → Gateway → 前端）比单元测试更重要。

### 2. 是否需要统一的事件命名前缀？

当前 Gateway 事件使用 `stream:message`、`thread:message` 作为前缀约定。方案中 Agent 事件使用 `agent:open-preview`、`agent:open-file`、`agent:notify`，保持了一致的 `agent:` 前缀。

但 `agent:event` 被拆分为三个独立事件类型，这种拆分的好处是：
- 前端可以按类型选择性监听（例如只关心 notify，不需要处理 open-preview）
- 事件 payload 可以按类型进行严格的 TypeScript 类型约束
- 避免在一个事件下用 `_event` 字段区分子类型

### 3. `_event` 内部字段的取舍

当前 `emit_event` 工具在 enrichedPayload 中添加了 `_event`、`_sessionId`、`_agentName`、`_timestamp`。方案中将它们提升为 `AgentEventMessage` 的结构化字段（`type`、`meta.sessionId`、`meta.agentName`、`meta.timestamp`），而不是嵌入 payload 中。这样：
- 前端接收时不需要解析 `_` 前缀的私有字段
- payload 保持干净，只包含业务数据
- meta 信息可以被中间层（Gateway）利用做路由/过滤

### 4. 前端 UI 实现的复杂度

三个事件的 UI 实现复杂度不同：

- **notify**：最简单，直接调用 toast 组件，已有现成基础设施
- **open-file**：中等，需要文件编辑器 / 工作区导航能力
- **open-preview**：最复杂，需要内嵌 iframe 或侧边预览面板

建议分阶段实现：先完成 notify（最快见效），再 open-file，最后 open-preview。

### 5. Publisher 的自动扫描机制

当前 Publisher 的加载方式需要进一步确认：是 Gateway 初始化时自动扫描 `src/main/publishers/` 目录，还是通过显式 import 加载？如果是自动扫描，新增文件无需额外注册。如果是显式加载，需要找到注册入口并添加 `import './AgentEventPublisher'`。

### 6. 安全考虑

`emit_event` 允许 Agent 发送自定义事件名（`z.string().describe(...)`）。方案中只桥接了三种预定义事件。Agent 传入的自定义事件名会被 `AgentEventType` 类型断言过滤。

可以考虑：
- 在 Publisher 中只转发已知的事件类型，未知事件记录日志但不转发
- 或者在 emit_event 工具中就验证 event 是否为合法类型
