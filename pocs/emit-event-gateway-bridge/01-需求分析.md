# emit_event 后端到前端事件链路缺失 - 需求分析

> 创建时间：2026-04-29
> 最近更新：2026-04-29

## 需求复述

`emit_event` 是 Agent/LLM 触发前端 UI 行为的工具。对 Agent 来说，它应该尽量简单：只表达“我要让前端做什么”和“附带什么数据”，不要暴露 Gateway、EventBus、前端组件、工作台状态等内部细节。

最终希望采用的消息模型是：

```ts
{
  type: 'agent:message',
  action: 'notify' | 'open-preview' | 'open-file' | string,
  payload: {
    text?: string,
    data?: Record<string, unknown>
  },
  meta: {
    sessionId?: string,
    agentName?: string
  },
  timestamp: number
}
```

核心边界：

- **Gateway 外层事件固定为 `agent:message`**
- **具体动作通过 `action` 表达**
- **payload 永远只保留两个字段：`text` 和 `data`**

这样后续新增 Agent UI 能力时，不需要继续膨胀成 `agent:open-preview`、`agent:open-file`、`agent:notify`、`agent:xxx` 一串顶层 Gateway 事件；只需要新增 action 的说明和前端 handler 分支。

## 需求背景

当前 `src/main/agent/tools/builtin/emit-event.ts` 的 JSDoc 声明：事件会通过 Gateway WebSocket 广播给所有连接的前端客户端。但实际代码只执行了：

```ts
eventBus.emit('agent:event', enrichedPayload);
```

这个事件没有后续监听者，因此事件在后端 EventBus 处丢失。

## 核心问题

### 问题一：EventBus 到 Gateway 缺桥

当前 Gateway Publisher 目录中已有：

| Publisher            | 转发的事件                                                     |
| -------------------- | -------------------------------------------------------------- |
| `StreamPublisher.ts` | `stream:message`、`stream:start`、`stream:end`、`stream:error` |
| `ThreadPublisher.ts` | `thread:message`                                               |
| `WorkerPublisher.ts` | `worker:status`、`worker:progress`、`worker:error`             |

但是没有 Agent Message 对应的 Publisher。

当前链路：

```text
emit_event 工具
  └─ eventBus.emit('agent:event', payload)
       └─ 无 Publisher 监听，事件丢失
```

目标链路：

```text
emit_event 工具
  └─ 规范化 action + payload(text/data)
       └─ eventBus.emit('agent:message', message)
            └─ AgentMessagePublisher
                 └─ Gateway WebSocket
                      └─ renderer gatewaySetup
                           └─ renderer eventBus
                                └─ agentEventsHandle 按 action 执行 UI 行为
```

### 问题二：外层事件不应该随 action 增长

如果把每个 Agent UI 能力都定义成 Gateway 顶层事件，会出现：

- `agent:open-preview`
- `agent:open-file`
- `agent:notify`
- `agent:xxx`

随着能力增加，`GatewayEventTypes`、Publisher、`gatewaySetup`、前端事件类型都会变得越来越臃肿。

更好的方式是固定一个通道：

- `agent:message`

然后在 message 中使用：

- `action`：表示要做什么
- `payload.text`：给用户看的主要文本
- `payload.data`：给程序用的结构化参数

### 问题三：payload 结构需要统一

旧思路中不同 action 有不同 payload：

- `open-preview`: `{ url, title }`
- `open-file`: `{ path }`
- `notify`: `{ message, level }`

这种方式类型更强，但后续扩展时每个 action 都要重新设计 payload 类型，工具描述也会越来越复杂。

新目标是统一 payload：

```ts
interface AgentMessagePayload {
  text?: string;
  data?: Record<string, unknown>;
}
```

字段语义：

- `text`：给人看的主要内容，例如通知文案、预览标题、文件说明
- `data`：给系统执行用的参数，例如 `url`、`path`、`level`

当前三种 action 的字段约定：

| action         | payload.text       | payload.data                |
| -------------- | ------------------ | --------------------------- |
| `notify`       | 通知文案，必填     | `{ level?: 'info' \| ... }` |
| `open-preview` | 预览标题，可选     | `{ url: string }`           |
| `open-file`    | 文件展示标题，可选 | `{ path: string }`          |

### 问题四：统一格式不等于放弃校验

payload 统一后，TypeScript 对每个 action 的 payload 约束会弱一些。因此必须在运行时按 action 校验：

- `notify` 必须有 `payload.text`
- `open-preview` 必须有 `payload.data.url`
- `open-file` 必须有 `payload.data.path`
- 未支持的 action 必须明确拒绝，不能静默成功

### 问题五：前端应接入现有事件分层

当前 renderer 已形成清晰分层：

- `gatewaySetup.ts`：把 Gateway 推送桥接到前端 EventBus
- `eventbus/event_handles/*EventsHandle.ts`：消费前端 EventBus 事件并执行业务逻辑

Agent Message 应沿用这层结构，而不是在任意组件中直接使用 `useGateway()` 监听。

## 约束条件

- Gateway 顶层事件固定为 `agent:message`
- 第一阶段只执行三种 action：`notify`、`open-preview`、`open-file`
- payload 格式固定为 `{ text?: string; data?: Record<string, unknown> }`
- 未知 action 或无效 payload 必须运行时拦截
- 后端 Publisher 应贴合现有 Gateway 自动扫描机制
- 前端消费应优先复用现有能力：
  - `useOpenFiles().openUrl`
  - `useOpenFiles().openFile`
  - `vue-sonner` 的 `toast`

## 验收目标

- Agent 调用 `emit_event` 后，后端发射 `agent:message`
- 前端能收到 `agent:message` 并按 `action` 执行 UI 行为
- `notify` 能显示 toast 通知
- `open-preview` 能打开工作台 URL 预览
- `open-file` 能打开工作台文件
- 未知 action 不会静默成功
- shared 类型固定为一个 Agent Message 通道，不随 action 增长
- 测试覆盖工具消息规范化、Publisher 转发、前端 handler 行为
