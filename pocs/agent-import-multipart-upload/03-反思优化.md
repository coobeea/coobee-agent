# 智能体导入接口 multipart 直传改造 - 反思优化

> 创建时间：2026-04-30
> 选定方案：上策（multipart/form-data 二进制直传）

## 边界情况

- **用户未选择文件**：前端由文件选择器保证不会调到 `importAgent(file)`；后端 `ctx.request.file` 为 undefined 时立即返回 400 `"file is required"`，不会走到 `importAgent(tempZipPath)`。
- **文件不是 ZIP**：`AgentImportExport.importAgent` 内部会进行 manifest.json / agent.json 校验，任何非法包结构都会返回 `{ success: false, error }`，400 走回前端，用户能看到明确错误提示。
- **超过 200MB 上限**：multer 会抛出 `LIMIT_FILE_SIZE`。该异常发生在业务 handler 之前，必须由上传包装中间件捕获，并返回 413 + 标准 `ApiResponse`。
- **临时文件清理失败**：finally 分支捕获 `fs.unlinkSync` 异常并只做 warn 日志，不影响接口返回，避免"清理失败掩盖业务成功"的问题。
- **同名文件重复上传**：multer 落盘时的 `filename` 中拼入了 `Date.now() + random slice`，不会撞车。
- **浏览器手动设置 Content-Type**：前端 `fetch` 未手动设置 Content-Type，浏览器会自动生成带 boundary 的 multipart。如果后续有人在 `ApiClient` 里加全局 header 注入，要注意不能污染到这里的 FormData 请求。

## 安全评估

- **内网监听**：Gateway 当前监听 `0.0.0.0:8765`，导入接口不做认证，与既有其它接口一致。不在本次改造范围内，但新增的 200MB 体积上限已经收窄了误用/攻击面。
- **ZipSlip**：`AgentImportExport` 是既有逻辑，本次未改动；该风险与本 POC 独立。
- **磁盘占满**：极端情况下用户反复上传 200MB 大包，如果 `importAgent` 调用失败且清理也失败，可能在 tmpdir 里累积垃圾。日常运行无风险，但长期可考虑增加一个启动期的 tmpdir 扫描兜底（超纲，不在本次）。
- **浏览器 CORS**：GatewayServer 全域 `cors({ origin: '*' })`，multipart 预检（OPTIONS）可以通过。

## 影响分析

- `@koa/multer` 的类型声明对 `koa` 的 `Request` 做全局合并，会**删掉** `body` 字段。项目里 12 处依赖 `ctx.request.body` 的路由文件（ChatRoutes、ConfigRoutes、FileRoutes、ThreadRoutes、ThreadlessRoutes、AgentRoutes）一旦 tsc 重新编译就会全部报错。
- 对策：新增 `src/main/types/koa-augment.d.ts`，通过 `declare module 'koa' { interface Request { body?: unknown; file?: MulterFile; files?: ... } }` 把 `body / file / files` 三个字段合并回去。既兼容 `koa-bodyparser`，又让 multer 单/多文件字段同时被静态识别。
- 非导入路由（JSON 接口）**完全不受影响**：中间件仍是 `bodyParser`，类型通过全局 d.ts 恢复，运行期行为与之前一致。
- `bodyParser` 配置保持默认（`jsonLimit: '1mb'`），这对普通 CRUD 接口是安全值，无需抬高。

## 性能与可维护性

- **内存曲线**：multer diskStorage 边收边写磁盘，主进程内存占用在上传期间保持常量。相比 base64 JSON 方案 42.6MB 字符串一次性驻留，显著改善。
- **吞吐**：multer 单机 + 本地回环（Electron 主进程和 Renderer 共享本机），瓶颈在磁盘写而不是网络，32MB 包的感知延迟基本不可察觉。
- **后续复用**：其它大文件上传接口（如知识库资源、附件、OCR 输入）可以直接复制 `importUpload` 模板，只改 `fileSize` 上限和落盘目录。
- **类型声明一次性偿还**：`koa-augment.d.ts` 是本次引入 multer 的最大"税"，但它同时把 `bodyParser` 注入的 body 也显式声明出来了，属于额外收益。

## 优化调整

1. **友好化文件大小超限提示**：用 Koa 中间件包一层 try/catch，捕获 `MulterError.code === 'LIMIT_FILE_SIZE'` 并返回 413 + 明确错误消息，而不是 Koa 默认 500。
2. **日志补全**：导入路由已新增 `Received upload: name=..., size=..., path=...` 一条 info 日志，便于后续排查体积和落盘位置。
3. **前端错误归一**：`importAgent` 的 try/catch 把网络层异常统一封装成 `ApiResponse`，和其它 API 的错误呈现保持一致。

## 最终方案

- 后端：`AgentRoutes.ts` 顶部新增 `importUpload = multer({ storage: diskStorage to os.tmpdir(), limits: 200MB })`，`/agents/import` 路由挂 `handleImportUpload` 包装中间件。包装中间件内部调用 `importUpload.single('file')`，将 `LIMIT_FILE_SIZE` 等上传错误转换成标准 `ApiResponse`；业务 handler 从 `ctx.request.file.path` 读取磁盘路径，直接传给既有 `AgentImportExport.importAgent(zipPath)`，finally 负责 unlink 临时文件。
- 前端：`importAgent(file)` 重写为 `new FormData(); formData.append('file', file, file.name); fetch(...)`，不手动设置 Content-Type。保持返回 `Promise<ApiResponse<ImportResult>>`，并对非 JSON 响应做兜底，UI 层零改动。
- 类型：新增 `src/main/types/koa-augment.d.ts`，通过接口合并把 `body / file / files` 重新注入 koa 的 `Request` 类型，解决 `@koa/multer` 全局覆盖导致的 12 处路由文件连带报错。
- 依赖：`package.json` 新增 `@koa/multer ^4.0.0`、`multer ^2.1.1`，devDependencies 新增 `@types/multer`、`@types/koa__multer`。
- 不改：`AgentImportExport`、`GatewayServer` 中间件链、其它任何路由、`ApiResponse` 契约、AgentView UI。
