# 智能体导入接口 multipart 直传改造 - 方案设计

> 创建时间：2026-04-30

## 上策：multipart/form-data 二进制直传

- **核心思路**：后端 `/agents/import` 改用 `@koa/multer` 做 multipart 解析，将上传文件直接落盘到系统临时目录；前端用原生 `FormData` + `fetch` 直接上传二进制，Content-Type 由浏览器自动生成带 boundary 的 `multipart/form-data`。
- **改动范围**：
  - 新增依赖 `@koa/multer` + `multer` + 类型
  - `AgentRoutes.ts` 引入 `multer.diskStorage`，路由挂 `importUpload.single('file')`
  - `api/agents.ts` 的 `importAgent(file)` 用 FormData 替换 base64 链路
  - 新增全局 `koa-augment.d.ts` 处理 `@koa/multer` 对 `koa` Request 类型的副作用合并
- **优势**：
  - 零冗余编码，32MB 就传 32MB，不再有 33% 的 base64 膨胀
  - 前端不再做大数组展开，彻底消除栈溢出风险
  - 后端不走 bodyParser 的 JSON 分支，与 1MB 默认限制解耦
  - 属于业界标准做法，后续其它大文件上传接口可直接复用该模板
  - multer 自动落盘到 tmpdir，路由里拿到 path 就可直接交给既有 `importAgent(zipPath)` 领域逻辑
- **劣势**：
  - 引入 2 个新依赖（`@koa/multer` + `multer`）
  - `@koa/multer` 的 d.ts 会替换 koa 的 Request 类型，触发项目内所有 `ctx.request.body` 的类型丢失，需要补一个全局接口合并声明

## 中策：保留 JSON 通道，但前端分块 base64 + 后端 bodyParser 扩容

- **核心思路**：前端用 32KB chunk 循环 `String.fromCharCode.apply(null, chunk)` 拼接后再 `btoa`，后端把 `bodyParser` 的 `jsonLimit` 调到 100MB。
- **改动范围**：
  - `api/agents.ts` 改分块编码
  - `GatewayServer.ts` 给 bodyParser 传 `jsonLimit/formLimit/textLimit` 配置
- **优势**：
  - 不新增依赖
  - 改动面最小（两处各改几行）
  - 现有接口契约不变
- **劣势**：
  - 33% 的 base64 膨胀仍然存在（32MB 变 42.6MB）
  - JSON 解析路径会把整段 base64 字符串一次性加载进内存并反序列化，较大包会造成主进程内存峰值陡增
  - `jsonLimit` 被抬高到 100MB 后，对所有走 JSON 的接口都生效，相当于拿掉了一道常见的 DoS 防线
  - 本质仍是反模式：把二进制硬塞进文本通道

## 下策：分片上传 + 后端合并

- **核心思路**：前端把 ZIP 按 5MB 切片，逐片上传；后端提供 `init / chunk / commit` 三个端点，服务端负责拼装成完整 zip 后交给 `importAgent`。
- **改动范围**：
  - 后端新增上传会话管理（sessionId、chunkIndex、checksum、超时回收）
  - 前端实现分片循环、断点续传、失败重试
  - 需要引入会话存储（内存 Map 或 Redis）
- **优势**：
  - 理论上支持任意大小、支持断点续传
  - 单次请求体小，对代理/网关友好
- **劣势**：
  - 相对于本次"单机 Electron 内部进程通信"的场景严重过度设计
  - 代码量是上策的 5 倍以上
  - 引入一堆需要自己维护的状态管理逻辑，出 bug 概率显著变高

## 方案对比

| 维度           | 上策（multipart）              | 中策（base64 扩容）       | 下策（分片上传）  |
| -------------- | ------------------------------ | ------------------------- | ----------------- |
| 实施成本       | 中（约 100 行差）              | 低（约 15 行差）          | 高（500+ 行）     |
| 长期收益       | 高                             | 低                        | 中                |
| 风险（前端）   | 零膨胀，零栈溢出               | 仍有大内存峰值            | 分片失败/重试复杂 |
| 风险（后端）   | 流式落盘，常量内存             | JSON 整体加载，内存峰值大 | 状态管理易出错    |
| 契约规范性     | 符合业界标准                   | 继续反模式                | 过度设计          |
| 对其他接口影响 | 几乎无（新增 d.ts 只增强类型） | 会抬高全局 JSON 上限      | 无                |

## 选定方案

**上策（multipart/form-data 二进制直传）**。

理由：

1. 本次 32MB 只是触发点，后续智能体包的体量只会越来越大，base64 扩容路线注定只是缓兵之计。
2. multer 磁盘存储天然契合"把上传文件交给 `importAgent(zipPath)` 领域函数"这种需要磁盘路径的消费模式，链路最短。
3. 业界标准做法，未来其它大文件上传接口（文件附件、知识库资源包等）可以直接复用该模板。
4. 相对于分片上传的过度设计，上策改动量可控（单接口改造），风险可控（不影响其它路由）。
