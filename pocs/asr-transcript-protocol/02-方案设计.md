# ASR 转写协议统一 - 方案设计

> 创建时间：2026-05-03

## 上策：定义完整的统一转写流协议

- **核心思路**：
  - 不再把 `partial/final` 当作唯一协议抽象，而是定义 provider 无关的统一下行消息。
  - 协议显式区分“已确认文本”和“当前草稿文本”，同时给出“当前应展示文本”的稳定构成方式。
  - 每条文本消息带上 turn/segment 边界与消息序号，前端按协议状态机消费，而不是按字符串长度猜测。
  - `asr_status` 继续保留，但只负责表达处理阶段，不再承担文本边界语义。
- **建议协议方向**：
  - 文本状态字段：
    - `committed_text`：已确认、不会回滚的文本快照
    - `draft_text`：当前正在修订中的草稿文本
    - `display_text`：可选，明确告诉前端当前应展示的文本，默认等于 `committed_text + draft_text`
  - 边界字段：
    - `turn_id` 或 `segment_id`
    - `revision`
    - `seq`
    - `is_final_turn`
  - 状态字段：
    - `asr_status`
    - `provider`
    - `latency_ms`
    - `buffered_ms`
- **provider 适配规则**：
  - 本地 ASR：
    - 停顿识别完成后，把结果并入 `committed_text`
    - 无实时草稿时可发送空 `draft_text`
  - 阿里云 ASR：
    - 实时修订内容映射到 `draft_text`
    - completed 后把该 turn 文本并入 `committed_text`，清空 `draft_text`
- **改动范围**：
  - `resources/workers/asr/server.py`
  - `src/renderer/src/composables/useAudioRecorder.ts`
  - 相关前端消费组件
  - 建议新增共享协议类型定义
- **优势**：
  - 从根上统一语义，后续接新 provider 成本最低。
  - 前端展示逻辑最稳定，不再依赖文本拼接技巧。
  - 能同时支持“简单全文展示”和“高级实时草稿展示”两类 UI。
- **劣势**：
  - 设计和改造成本最高。
  - 需要对现有本地 ASR 和阿里云适配都做协议层调整。

## 中策：保留 `partial/final`，补齐确认边界字段

- **核心思路**：
  - 维持 `partial/final` 兼容外形，但补充显式语义字段，让前端知道当前收到的是“草稿”还是“确认快照”。
  - 例如增加：
    - `text_mode`: `draft` | `committed_snapshot` | `final_session`
    - `turn_id`
    - `revision`
    - `replace_from`
  - 前端根据这些字段决定是覆盖当前草稿、追加确认文本，还是更新整段显示。
- **改动范围**：
  - 主要集中在 `resources/workers/asr/server.py`
  - `useAudioRecorder.ts` 要从“长度截断”改成“模式驱动消费”
  - 页面组件改动相对较小
- **优势**：
  - 可以逐步演进，兼容现有消息格式。
  - 比上策实施更快。
  - 比当前字符串拼接方式可靠很多。
- **劣势**：
  - 协议心智仍然绕在 `partial/final` 上，长期可读性一般。
  - 随 provider 增多，协议继续膨胀的风险较大。

## 下策：仅做前端兼容性修补

- **核心思路**：
  - 不调整服务端对外协议，只在前端增加更强的文本合并策略。
  - 例如把 `InsightView` 改成类似 `VoiceConversationInput` 的 overlap merge，并尽量兼容回改。
- **改动范围**：
  - `src/renderer/src/composables/useAudioRecorder.ts`
  - `src/renderer/src/views/InsightView.vue`
  - `src/renderer/src/components/chat/VoiceConversationInput.vue`
- **优势**：
  - 见效最快。
  - 对现有服务端影响最小。
- **劣势**：
  - 根因没有解决，协议债务继续存在。
  - 每个页面都要继续做“聪明但脆弱”的兼容。
  - 新增 provider 时仍会重复踩坑。

## 方案对比

| 维度 | 上策 | 中策 | 下策 |
|------|------|------|------|
| 实施成本 | 高 | 中 | 低 |
| 协议清晰度 | 高 | 中 | 低 |
| 长期收益 | 高 | 中高 | 低 |
| 前端稳定性 | 高 | 中高 | 中低 |
| provider 扩展性 | 高 | 中 | 低 |
| 技术债风险 | 低 | 中 | 高 |

## 推荐方案

建议选择 **上策**，但实施方式采用“分阶段落地”：

1. 先定义统一协议和共享类型，不急着一次性改完所有 UI。
2. 先改 ASR Worker 适配层，让本地 ASR 和阿里云 ASR 输出同一语义。
3. 再改 `useAudioRecorder.ts`，把“长度截断消费”替换为“状态机消费”。
4. 最后让 `InsightView` 和 `VoiceConversationInput` 都只消费统一结果。

这样做的原因是：

- 当前问题已经被证明是协议层问题，不是单个页面逻辑问题。
- 用户明确要求把协议层作为通用基建优先建设。
- 之前的中策 `asr_status` 已经证明“补丁式增强”无法解决文本语义不一致。

## 选定方案

当前建议先按 **上策** 进入下一阶段细化，重点不是立刻大改界面，而是先把统一协议字段、状态机和兼容迁移路径设计清楚。
