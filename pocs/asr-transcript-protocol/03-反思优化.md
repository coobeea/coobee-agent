# ASR 转写协议统一 - 反思优化

> 创建时间：2026-05-03
> 选定方案：上策

## 边界情况

- 本地 ASR 不是逐字流式识别，而是 VAD 停顿后整段识别，因此协议不能强制要求 provider 一定持续输出 `draft_text`。
- 云端实时 ASR 可能会频繁回改前文，因此协议不能假设文本只会单调追加，必须有 `revision` 或同类版本语义。
- 同一会话可能包含多个 turn/segment，协议必须区分“当前语段完成”与“整场会话结束”。
- 断开连接时的 `final` 不能再承担多重语义，否则前端仍会混淆“尾段补识别”和“整场最终结果”。
- 若消息乱序或重复到达，前端应能依据 `seq` 或等价序号丢弃旧消息。

## 兼容性评估

- 现有业务组件很多地方默认依赖 `partial/final`，不能一刀切直接删除旧字段。
- 更稳妥的路径是：
  - 第一阶段新增统一字段和共享类型；
  - 第二阶段前端优先消费新字段；
  - 第三阶段再逐步弱化旧字段。
- 如果需要兼容旧版本前端，服务端可以在过渡期同时发送：
  - 旧字段：`partial` / `final`
  - 新字段：统一转写协议字段

## 对现有功能的影响

- `useAudioRecorder.ts` 会从“基于长度截断的字符串处理”切换成“基于协议状态的文本组装”，这是本次最关键的消费逻辑升级。
- `InsightView.vue` 可以继续保持当前简单全文展示，只需要改为显示统一协议给出的当前文本。
- `VoiceConversationInput.vue` 里现有的 overlap merge 逻辑会从“主逻辑”降级为“兼容兜底逻辑”，复杂度可下降。
- `asr_status` 仍有价值，但定位会更纯粹，只负责表达语音活动和识别阶段。

## 性能与可维护性

- 明确 `committed_text` / `draft_text` 后，前端无需在每次消息到达时做大量字符串猜测，可维护性明显提升。
- 如果每次都发送完整 `display_text`，消息体会稍大；但在当前录音场景下，可读性和稳定性收益通常大于这部分成本。
- 若后续担心长会话消息过大，可进一步演进为：
  - 快照消息 + 增量 patch
  - 或按 turn 粒度下发结构化结果
- 从长期看，协议层集中收敛 provider 差异，比在多个页面重复做兼容更省成本。

## 优化调整

- 统一协议中建议保留一个“前端可直接渲染”的字段，优先命名为 `display_text` 或在共享类型中明确定义其推导规则。
- 明确两层完成语义：
  - `turn_final`：当前语段已经确认
  - `session_final`：当前连接或会话的最终文本已经收敛
- 为协议增加来源与调试字段，便于后续排查：
  - `provider`
  - `turn_id`
  - `seq`
  - `latency_ms`
- 为迁移期定义兼容策略，避免前后端灰度阶段出现“双重拼接”。

## 最终方案

采用统一转写流协议作为长期基建方向，核心原则如下：

1. 文本语义显式化，不能再让 `partial/final` 承担多义角色。
2. provider 差异收敛在 ASR Worker 适配层，不泄漏到业务组件。
3. 前端统一按状态机消费，业务页面只拿“当前应展示文本”和必要状态。
4. 迁移阶段兼容旧字段，但新逻辑优先依赖统一字段。

这样可以把当前“录音效果不好”的问题，从页面层 patch，升级为可复用、可扩展、可调试的底层协议基建。
