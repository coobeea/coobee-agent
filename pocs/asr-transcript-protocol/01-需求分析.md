# ASR 转写协议统一 - 需求分析

> 创建时间：2026-05-03

## 需求背景

当前录音转写体验的主要问题不在界面，而在 ASR 协议层语义不稳定。前端录音链路已经能采集音频、通过 WebSocket 发送到 ASR Worker，并接收 `partial`、`final`、`asr_status` 等消息，但不同 provider 对这些字段的含义并不一致，导致前端只能靠长度截断、文本拼接和经验性合并去“猜”服务端想表达什么。

这在界面上会表现为：

- 录到的内容不能自然、完整、快速地展示出来。
- 不同 provider 下同一套前端逻辑表现不一致。
- 一旦 provider 的 `partial` 出现回改、重置或分段边界变化，前端容易重复追加、漏字或错误截断。

当前协议问题已经从单个页面体验问题，升级为通用底层基建问题。后续 Insight、语音对话、会议记录等所有实时录音场景，都会依赖这一层协议。

## 当前链路现状

### 1. 前端消费假设

`src/renderer/src/composables/useAudioRecorder.ts` 当前会：

- 读取服务端 `partial` / `final` / `asr_status`
- 用 `sentTextLength` 对 `partial` / `final` 做 `substring()` 截断
- 把截断后的文本交给上层组件

这意味着前端默认假设：

- `partial` 是可安全按长度截断的“完整累计文本”或“单调增长文本”
- `final` 与 `partial` 共享同一文本坐标系
- provider 不会频繁回改前文

但这个假设并不成立。

### 2. 本地 ASR 的真实语义

`resources/workers/asr/server.py` 中本地 `local_asr_stream()` 的行为是：

- 持续接收 PCM 音频
- 用 VAD 检测“说话开始 / 持续说话 / 静音结束”
- 在停顿后把整段音频送进识别
- 把识别结果追加到 `committed_text`
- 对前端发送 `{"partial": committed_text}`
- 连接结束时再发送一次 `{"final": committed_text}`

也就是说，本地 ASR 当前的 `partial` 并不是“实时草稿文本”，而是“已经确认并累计提交的整段文本快照”。

同时，服务端内部其实已经维护了关键边界信息：

- `recognized_pos`
- `committed_text`
- `speech_start_pos`
- `silence_start_pos`

但这些边界并没有透出到统一文本协议里。

### 3. 阿里云 ASR 的真实语义

`resources/workers/asr/server.py` 中 `aliyun_asr_stream()` 当前会：

- 把阿里云 realtime 事件转换成对外的 `partial` / `final`
- 非 completed 事件时发送 `{"partial": text}`
- completed 事件时发送 `{"final": text}`

这里的 `partial` 更接近“当前语段的实时识别草稿”，`final` 更接近“当前语段的最终确认文本”。

这与本地 ASR 的语义明显不同：

- 本地：`partial = 累计 committed 快照`
- 阿里云：`partial = 当前 turn 草稿`

### 4. 现有 `asr_status` 的定位

当前 `asr_status` 只补充了处理阶段：

- `speech_start`
- `speech_active`
- `speech_end`
- `recognizing`
- `recognized`

它解决了“服务端此刻在做什么”的可见性问题，但没有解决“文本结果到底处于什么确认阶段、文本边界在哪里、如何稳定消费”的协议问题。

## 核心目标

- 定义一套 provider 无关、前后端都能稳定消费的 ASR 转写协议。
- 明确 `partial`、`final` 或替代字段的统一语义，不再依赖“猜测式拼接”。
- 让前端可以直接根据协议还原“当前应展示的文本”，而不是用长度差和重叠合并做兜底。
- 让本地 ASR、阿里云 ASR 以及后续新增 provider 都能通过适配层输出同一语义。
- 保留 `asr_status` 这类过程状态，但把它从“文本协议补丁”升级为“文本协议的辅助状态”。

## 根因总结

当前录音效果“不自然、不迅速、不完整”的根因主要有四类：

1. `partial/final` 缺少统一定义，不同 provider 各说各话。
2. 前端把不同 provider 的文本流当成同一协议消费。
3. 服务端内部已有边界状态，但没有显式暴露给前端。
4. 前端当前主要依赖“按长度截取”和“字符串拼接”恢复文本，天然脆弱。

## 协议层需要回答的关键问题

- `partial` 到底表示“当前完整展示文本”“当前语段草稿”，还是“新增增量”？
- `final` 到底表示“当前语段确认”“整场会话最终文本”，还是“连接结束时的兜底快照”？
- 是否需要显式区分：
  - 已确认文本
  - 当前草稿文本
  - 当前应展示文本
  - turn / segment 边界
  - 消息序号或修订版本
- 前端在不做复杂 UI 改造的前提下，如何直接拿协议结果自然展示全文？

## 约束条件

- 不能只修某一个页面，协议必须能被 `InsightView`、`VoiceConversationInput` 等多个场景复用。
- 不优先修改界面结构，先收敛协议定义和消费语义。
- Gateway 当前是透明代理，优先在 ASR Worker 适配层和前端 `useAudioRecorder` 之间解决。
- 需要兼容本地 ASR 的 VAD 分段识别模式，也需要兼容云端 provider 的实时修订模式。
- 尽量避免让业务组件直接理解 provider 差异，差异应被收敛在协议层。

## 涉及范围

- 模块：
  - ASR Worker provider 适配层
  - 前端语音录音 composable
  - Insight 实时转写展示
  - 语音对话输入
- 文件：
  - `resources/workers/asr/server.py`
  - `src/renderer/src/composables/useAudioRecorder.ts`
  - `src/renderer/src/views/InsightView.vue`
  - `src/renderer/src/components/chat/VoiceConversationInput.vue`
  - 可能新增 `src/shared/` 下的协议类型定义
- 接口：
  - ASR Worker WebSocket 下行消息协议

## 期望产出

- 一份明确的转写协议定义，包括字段语义、边界规则、provider 适配约束。
- 一套前端统一消费方式，业务组件不再直接处理 provider 差异。
- 后续可实施的改造清单，用于逐步替换现有 `partial/final` 的脆弱消费逻辑。
