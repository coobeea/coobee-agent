# workspace/project 命名收敛 V1 · 需求分析

## 背景

当前系统里有一个长期命名漂移：

- 用户和前端更自然地把 Agent 的业务目录理解为“项目”。
- 运行时和后端大量使用 `workspace`、`workspaceRoot`、`workspacePath`。
- 物理目录当前是 `.home/agents/{agentId}/workspace/`。
- Skill 搜索来源里还有 `SkillSearchPathKind = 'workspace'`，它实际表达的是“会话临时技能来源”，不是 Agent 业务项目。

这会带来两个直接问题：

1. 用户、前端、后端、LLM 之间需要不断翻译“project / workspace / dataDirectory”。
2. LLM 看到 `<runtime_environment>` 或 `<skill_discovery>` 里的 `workspace` 后，容易把“会话临时技能来源”和“Agent 业务目录”混在一起。

## 本轮判断

“命名一致性”方向是对的，但不应该第一版就把整个仓库里的 `workspace` 全部机械改成 `project`。

原因：

- `workspaceRoot` 在 sandbox、tool、runtime builder 里是通用工程术语，表示工具执行根目录或沙箱边界，不完全等同于用户理解的“项目”。
- HTTP/RPC 字段、事件 payload、工具上下文一次性全改，会制造很大的回归面。
- 当前全量类型检查本身还有既有债务，不能把大规模 rename 依赖在“全仓库立即类型绿灯”上。

所以 V1 先做一版“对用户和 LLM 最关键的命名收敛”，把真正会影响理解和路径落点的部分收住。

## V1 核心目标

1. **物理目录收敛**
   - Agent 业务目录从 `.home/agents/{agentId}/workspace/` 改为 `.home/agents/{agentId}/project/`。
   - 运行时默认业务数据、工具 cwd 继续指向这个目录。

2. **运行时提示收敛**
   - `<runtime_environment>` 中对 LLM 展示 `project`，不再展示 `workspace` 作为业务目录名称。
   - `PromptAssemblyService` 的 `<workspace_context>` 改为 `<project_context>`。
   - 新增 `COOBEE_PROJECT` 环境变量，作为脚本和技能推荐使用的业务项目目录变量。

3. **Skill 来源命名收敛**
   - `SkillSearchPathKind` 中的 `'workspace'` 改为 `'session'`。
   - 该来源表达“当前会话临时技能来源”，不再和 Agent 业务项目同名。

4. **前端语义收敛**
   - 面向用户的文案统一使用“项目”或“业务项目”。
   - 前端不再把 session 目录叫作 workspace。

## V1 非目标

本轮不做以下大规模改名：

- 不把所有 `workspaceRoot` 机械改成 `projectRoot`。
- 不强制删除所有 `workspace` 变量名。
- 不一次性改 HTTP/RPC API 字段。
- 不一次性改 `WorkspaceEvents` 等历史事件枚举。
- 不要求全仓库 grep `workspace` 清零。
- 不批量改已结案 POC 或历史日志。

这些可以作为 V2，在 V1 跑稳后再判断是否值得继续。

## 成功判定

- 新建或运行 Agent 时，业务目录使用 `.home/agents/{agentId}/project/`。
- 旧 `.home/agents/{agentId}/workspace/` 能通过一次性迁移进入 `project/`。
- `<runtime_environment>` 里对 LLM 展示 `project`，不把业务目录称为 `workspace`。
- `<project_context>` 能读取 `project/` 根目录下的上下文 Markdown。
- `SkillSearchPathKind` 第五档改为 `'session'`，提示词中不会再出现“workspace skill source”。
- 关键测试通过：路径布局、prompt 组装、SkillManager、工具 cwd、文件树展示。
