# workspace/project 命名收敛 V1 · 反思优化

## 为什么不做全量 rename

全量把 `workspace` 改成 `project` 看起来彻底，但第一版风险过高：

- `workspaceRoot` 是工具执行和 sandbox 边界里的稳定术语，很多测试和内置工具依赖它。
- `WorkspaceEvents` 这类事件名可能还有历史调用点，第一版改动收益不高。
- HTTP/RPC 字段如果一次性全部切换，会把前端 store、API types、事件桥接一起拉进来。
- 当前仓库全量 typecheck 已有既有错误，无法用“全仓库类型绿灯”承接巨大 rename。

所以 V1 应该把力量放在“真实业务目录”和“LLM 可见语义”上。

## 已固定决策

### D1：SkillSearchPathKind 第五档改为 `'session'`

理由：

- 它表达的是会话作用域的临时 Skill 来源。
- 和 `sessionId`、`sessionDir` 的语义一致。
- 不再污染 `project` 这个业务目录概念。

### D2：`<workspace_context>` 改为 `<project_context>`

理由：

- 这是 LLM 可见内容，必须和业务目录名称一致。
- 如果 prompt 里继续出现 workspace，模型仍会沿用旧称呼。

### D3：旧 `.home/workspaces/{sessionId}` 迁移逻辑 V1 暂不删除

理由：

- 它不是运行期 fallback，而是一次性历史数据搬迁能力。
- 仍可能存在用户跳过中间版本、直接升级到 V1 的情况。
- 删除这段迁移会增加数据丢失风险。

处理方式：

- 运行时不从旧路径读取。
- 迁移函数可以继续读取旧路径，把历史会话产物搬到 `sessions/{sessionId}`。
- 后续确认用户数据全部进入新布局后，再做清理。

### D4：采用单个窄 PR，而不是 6 个分层 PR

理由：

- V1 范围已经收窄，单 PR 更容易保证运行态完整。
- 分层 PR 在字段改名场景下容易出现中间态断编译。

### D5：迁移入口放到启动早期 hook

理由：

- 目录迁移必须早于 Agent system 初始化。
- 否则后续模块可能提前创建空 `project/`，掩盖迁移冲突。

## 需要特别避免的误区

1. 不要把 `workspaceRoot` 在工具系统里机械改成 `projectRoot`。
2. 不要把所有历史文档里的 workspace 一次性替换，历史快照应保留真实性。
3. 不要把 session 目录叫 project。`project` 只表示 Agent 业务目录。
4. 不要为了“grep 清零”引入大量 alias 或注释噪音。

## 最终 V1 边界

V1 完成后允许代码里仍出现 `workspace`，但必须符合以下语义：

- sandbox/tool/runtime 内部执行根目录术语。
- 历史迁移读取旧路径。
- 历史文档或已结案 POC。
- 明确标注 deprecated 的短期 alias。

不允许出现：

- prompt 中把业务目录叫 workspace。
- UI 中把 Agent 业务项目叫 workspace。
- Skill 来源 kind 继续叫 `'workspace'`。
- 新建物理目录继续使用 `.home/agents/{agentId}/workspace/`。
