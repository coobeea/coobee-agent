# Worker 前端对接方式 - 方案设计

> 创建时间：2026-04-29

## 上策：Gateway 全代理 Worker 数据通道

- **核心思路**：
  - 前端不直接连接 Worker 端口。
  - 所有 Worker 业务请求都通过 Gateway：
    - Worker 状态：`worker.list` / `worker:status`
    - ASR：`gateway/ws` 内部转发 PCM 和识别结果
    - TTS：Gateway 转发文本和音频结果
    - OCR：Gateway HTTP/RPC 或 Gateway WebSocket 转发
  - Worker 端口只对主进程可见，前端只认识 Gateway。

- **改动范围**：
  - 主进程新增 Worker 数据代理层。
  - Gateway 协议要支持二进制或 base64 流式消息。
  - 前端 VoicePanel、TTS、OCR 全部改为调用 Gateway Worker client。

- **优势**：
  - 安全边界最清晰，Worker 端口无需暴露给前端。
  - 对局域网访问友好，只要 Gateway 可达即可。
  - 未来权限、鉴权、审计、限流都可以集中在 Gateway。
  - 前端业务组件完全不需要理解 Worker 端口。

- **劣势**：
  - 实施成本最高。
  - ASR 二进制音频和 TTS 音频需要 Gateway 转发，会增加协议复杂度。
  - 大流量音频转发可能给主进程带来额外压力。
  - 短期会推翻旧项目已验证的直连方式。

## 中策：Gateway 管理通道 + Worker 直连数据通道（推荐）

- **核心思路**：
  - 保留旧项目已经验证的两条通道：
    - 管理通道走 Gateway：状态、启停、配置、模型切换。
    - 数据通道直连 Worker：ASR/TTS/OCR 的 HTTP/WebSocket。
  - 不让业务组件散落拼 URL，而是新增统一前端 client：
    - `WorkerRegistryClient`：从 `useWorkerStore` 获取 Worker 状态和端口。
    - `AsrWorkerClient`：封装 `/ws/asr` 的连接、PCM 发送、结果回调。
    - `TtsWorkerClient`：封装 `/ws/tts` 的文本发送、音频解码。
    - `OcrWorkerClient`：封装 `/api/ocr` 和 `/ws/ocr`。

- **改动范围**：
  - 保留现有 `WorkerMethods`、`workerStore`、`StatusBar`、`WorkersSettings`。
  - 将 `VoicePanel.vue` 里的 ASR/TTS 直连逻辑下沉到 client/composable。
  - 新增 OCR client。
  - 补一份 Worker 端点契约类型，约束每类 Worker 的请求/响应格式。

- **优势**：
  - 和旧项目一致，迁移成本低。
  - 实时音频不经过主进程二次转发，性能和延迟更好。
  - 前端使用仍然简单：业务组件只调用 client，不直接拼端口。
  - 当前已做的设置页、状态栏、store 都能继续使用。

- **劣势**：
  - Worker 端口仍然暴露给前端运行环境。
  - 局域网 Web 访问时，如果 Worker 只绑定 `127.0.0.1`，外部浏览器无法直连。
  - 如果 Worker 绑定 `0.0.0.0`，又会带来端口暴露和鉴权问题。
  - 需要约束前端只通过 client 使用 Worker，否则逻辑仍会散。

## 下策：继续在组件里按需直连 Worker

- **核心思路**：
  - 维持现状：业务组件从 `workerStore` 拿端口，自行构造 WebSocket/HTTP URL。
  - 只补齐缺失的 OCR 调用和少量状态展示。

- **改动范围**：
  - 最少，只改具体业务组件。
  - 不新增统一 client 层。

- **优势**：
  - 最快能跑通。
  - 基本照搬旧项目做法。

- **劣势**：
  - 组件耦合 Worker 端点和协议。
  - 未来更换 Gateway 代理、加鉴权、改端点会很痛。
  - 连接重试、错误处理、资源释放会重复实现。
  - 不符合“外部使用最简单”的原则。

## 补充：Gateway 代理模式后的推荐调整

进一步分析 Gateway 代理后，推荐从原来的“前端直连 Worker 数据通道”调整为：

```text
Gateway 管理通道 + Gateway Worker 透明代理数据通道
```

也就是：

- Worker 生命周期、状态、配置仍然通过 `worker.*` RPC 和 `worker:status`。
- ASR/TTS/OCR 业务数据不再由前端直连 Worker 端口，而是通过 Gateway 透明转发到 Worker。
- Worker 仍然只绑定本机地址，前端和外部浏览器只认识 Gateway。

这个方案细节见 `07-Gateway代理模式.md`。

## 暂定建议

暂定推荐“Gateway 透明代理方案”：管理通道走 Gateway RPC，业务数据通道走 Gateway Worker Proxy。

理由：

- 保留旧项目 Worker 协议，不需要改 ASR/TTS/OCR Python 服务。
- 前端外部使用最简单，只连 Gateway。
- Worker 端口不暴露给前端，局域网访问更可控。
- ASR/TTS 二进制或音频数据可以原样透传，不必塞进 JSON RPC。

需要继续讨论的关键点：

- 是否要求 Web/LAN 访问也支持语音和 OCR Worker。
- Gateway Worker Proxy 第一版是否只支持 ready Worker。
- HTTP proxy 是否先只支持 JSON body，后续再支持 multipart/raw body。
- 是否要为 Gateway proxy 加 token、origin 校验或权限策略。
