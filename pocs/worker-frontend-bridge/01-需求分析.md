# Worker 前端对接方式 - 需求分析

> 创建时间：2026-04-29

## 需求背景

coobee-agent 里的 ASR、TTS、OCR 等 Worker 是由主进程启动的独立服务。每个 Worker 有自己的端口、健康检查和业务接口，前端既要能看到 Worker 是否可用，也要能在业务场景中调用它们。

当前已经迁移了 Worker 目录、Worker 生命周期管理、设置页和状态栏，但还需要明确一个架构问题：前端到底是通过 Gateway 间接调用 Worker，还是直接连 Worker 自己的 HTTP/WebSocket 服务。

旧项目 `/Users/lifeng/git/git_agents/coobee-ai` 的实现是典型的“两条通道”：

- 管理通道：前端通过 Gateway RPC 调用 `worker.list/start/stop`，并通过 Gateway 事件接收 Worker 状态。
- 数据通道：前端拿到 Worker 的 `port` 后，直接连接 Worker 的业务端点，例如 `ws://host:{asrPort}/ws/asr`、`ws://host:{ttsPort}/ws/tts`。

## 核心目标

1. 明确 Worker 对接的职责边界：主进程负责启动和状态，前端负责业务消费，还是统一由 Gateway 代理。
2. 保持外部使用简单：业务组件不应该到处拼端口、拼路径、猜协议。
3. 支持实时场景：ASR/TTS 需要低延迟、长连接、二进制音频流。
4. 支持设置和状态展示：设置页、状态栏、语音面板都能复用同一份 Worker 状态。
5. 为后续 OCR、语音、模型配置、Worker 插件化留下清晰扩展点。

## 约束条件

- Worker 是独立 FastAPI 服务，端口来自 `resources/workers/{name}/worker.json`。
- Worker 由 `WorkerManager` 启动，启动时注入 `--host`、`--port` 和运行时环境变量。
- Gateway 已经是前后端统一管理通道，适合 RPC、事件和状态同步。
- ASR/TTS 的实时数据通道需要 WebSocket，ASR 还涉及二进制 PCM 数据。
- 默认 `VITE_SERVER_HOST` / `Env.main.serverHost` 是 `127.0.0.1`；如果未来支持局域网 Web 访问，直连 Worker 端口会遇到安全和可达性问题。

## 旧项目对接方式复盘

### Worker 状态与生命周期

- `useWorkerWs.ts`
  - 监听 Worker 状态事件。
  - 调用 `worker.list` 获取列表。
  - 调用 `worker.start` / `worker.stop` 启停 Worker。
  - Gateway 重连后自动刷新 Worker 列表。

- `stores/worker.ts`
  - 保存 `Map<workerName, WorkerStatusInfo>`。
  - 暴露 `workerList`、`getWorker()`、`isReady()`。
  - 暴露 `asrReady/asrPort/ttsReady/ttsPort`。

- `StatusBar.vue`
  - 读取 `workerStore.workerList`。
  - 展示 Worker 图标、名称、状态点。
  - 点击 stopped/error 的 Worker 会启动，点击 ready 的 Worker 会停止。

### ASR 数据通道

- `VoicePanel.vue` 和 `useAudioRecorder.ts` 在 `workerStore.asrReady && workerStore.asrPort` 后连接：

```text
ws://{configManager.getHost()}:{asrPort}/ws/asr
```

- 前端通过 Web Audio API 采集麦克风。
- 前端将 Float32 音频降采样为 16kHz，再转为 Int16 LE。
- 前端按 250ms 左右分片，通过 WebSocket 发送二进制 PCM。
- Worker 返回 JSON：
  - `{ status: "ready" }`
  - `{ partial: "..." }`
  - `{ final: "..." }`

### TTS 数据通道

- `VoicePanel.vue` 和 `useTtsPlayback.ts` 在 `workerStore.ttsReady && workerStore.ttsPort` 后连接：

```text
ws://{configManager.getHost()}:{ttsPort}/ws/tts
```

- 前端发送 JSON：

```json
{ "text": "你好", "speaker": "xiaoxiao" }
```

- Worker 返回 JSON：
  - `{ status: "processing" }`
  - `{ audio: "<base64>", "format": "mp3|wav" }`
  - `{ done: true }`

- 前端把 base64 音频转成 ArrayBuffer，再用 Web Audio API 播放。

### OCR 数据通道

旧 Worker 提供：

- `POST /api/ocr`
- `WS /ws/ocr`

但旧项目前端里 OCR 消费相对独立，没有像 ASR/TTS 一样形成统一组件入口。迁移到 coobee-agent 时需要补一个明确的 OCR client。

## 当前 coobee-agent 已有实现状态

已实现：

- `src/main/rpc/WorkerMethods.ts`
  - `worker.list/start/stop/modelsGet/configGet/configUpdate`
- `src/shared/events/worker.ts`
  - `worker:status/progress/error` 类型定义
- `src/renderer/src/stores/worker.ts`
  - 前端统一 Worker 状态 store
- `src/renderer/src/components/StatusBar.vue`
  - 全局 Worker 状态展示和启停入口
- `src/renderer/src/views/settings/WorkersSettings.vue`
  - Worker 管理设置页
- `src/renderer/src/components/agent/VoicePanel.vue`
  - 当前仍沿用旧项目方式，直接连接 `/ws/asr` 和 `/ws/tts`

尚未完全确认：

- 是否允许前端长期直接连接 Worker 端口。
- OCR 前端消费方式是否也应该统一。
- 局域网 Web 访问时，Worker 端口如何暴露、鉴权、代理。
- 是否需要一个统一的 `WorkerClient` 层，避免业务组件直接拼 URL。
