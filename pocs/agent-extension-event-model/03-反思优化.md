# Agent 扩展模型收敛 - 反思优化

> 创建时间：2026-04-24
> 选定方案：中策

## 一、边界情况

### 1. `message_received` 是否也应该改名

结论：**暂时保留**。

原因：

- 它本身已经是一个清晰的通知事件
- 语义没有歧义
- 没必要为了“全改成 started/completed”而硬改一个已经足够好的名字

### 2. `after_tool_call` 是否要补一个开始事件

结论：**当前不强制新增**。

原因：

- 现有 `prepare_tool_call` 已覆盖“调用前”的治理需求
- 当前最需要的是把“通知”和“拦截”分清，而不是追求事件绝对成对
- 如果后续确实有监听工具调用开始的稳定需求，再增加 `tool_call_started`

### 3. `session_start / session_end` 是否一定要替换成 `run_*`

结论：**应该替换**。

原因：

- 当前执行链里的触发时机并不是“会话实体被创建/销毁”
- 继续保留 `session_*` 只会让未来读代码的人误会

### 4. 本轮是否应该把第一个业务扩展场景定死

结论：**不应该**。

原因：

- 具体业务场景本身还在讨论
- 如果场景没定，就不该先反推目录结构和执行模型
- 当前更应该优先把 runtime 边界和扩展目录收干净

### 5. `resources/extensions/` 是否应该先做成通用目录

结论：**应该**。

原因：

- 目录先建立起来，后续无论挂哪个场景都顺
- 可以避免文档因为具体业务场景来回重写
- 也更贴近“类似旧仓库 extensions 目录”的原始诉求

## 二、安全与稳定性评估

本次调整风险主要来自三类：

1. **代码级 rename 漏改**
2. **payload 语义变化导致测试失效**
3. **在具体业务场景未定时，过早把抽象设计绑死**

由于当前扩展机制尚未正式使用，不需要对外兼容，因此前两类风险主要是仓库内部可控风险。  
第三类风险在这轮更值得注意：如果文档过早绑定某个具体场景，后面每轮讨论都要大改，反而会让 POC 失真。

## 三、对现有功能的影响

### 正向影响

- 扩展 API 边界更清楚
- 压缩、Turn、Run、Tool 四类 Agent 生命周期更容易理解
- `resources` 下终于有稳定扩展目录，不再只有 agents / skills
- POC 会更稳，不会因为具体场景还没定而反复来回

### 需要注意的影响

- `run_completed` 会吸收 `agent_end` 的职责，因此 `session_end` 应同步移除，避免重复事件
- 文档中凡是提到 `before_agent_start / after_tool_call / before_compaction` 的地方都要一起更新
- 如果 `ExtensionApi.on()` 暂时保留，类型提示必须已经分出 Event / Interceptor，不然外部感知不到这次收口
- 具体业务场景后续确定后，还需要补一轮“如何挂接到扩展机制”的设计

## 四、优化后的最终方案

### 1. 整体架构拆成两层

#### Runtime 扩展层

用于 Agent 运行期：

##### Agent Event

- `message_received`
- `run_started`
- `run_completed`
- `turn_started`
- `turn_completed`
- `tool_call_completed`
- `compaction_started`
- `compaction_completed`

##### Agent Interceptor

- `prepare_run_input`
- `prepare_tool_call`
- `transform_tool_result`

#### 内置扩展目录

用于承载当前仓库内置、受控扩展包：

- 根目录：`resources/extensions/`
- 当前先不绑定具体业务扩展场景

### 2. Runtime 内部事件移出默认公开面

以下点不再作为默认公开扩展能力：

- `message_queued`
- `message_dequeued`
- `queue_drain_start`
- `model_resolved`
- `model_fallback`

如后续确实需要，可单独设计为：

- `experimentalRuntimeEvents`
- `diagnosticEvents`
- 或内部专用调试事件流

### 3. `resources/extensions/` 的最终定位

它是：

- 内置扩展包目录
- 当前仓库的受控资源入口
- 与 runtime 扩展并列的一层

它不是：

- runtime hook 代码目录
- 技能目录
- 任意第三方插件市场

### 4. API 与目录的逐步收口路径

#### 第一步：先完成 runtime 命名和类型收敛

- 统一字符串名字
- 统一 payload 字段
- 在现有 `api.on()` 基础上完成 runtime 扩展收口

#### 第二步：补齐 `resources/extensions/`

新增：

```text
resources/extensions/
```

并在 README 中明确目录边界。

#### 第三步：具体业务场景后续单独讨论

等场景本身讨论清楚后，再继续补：

- 扩展包目录结构
- 具体执行链路
- 相关 service / policy / loader 设计

### 5. 建议的落地顺序

1. `types.ts` 中拆出 `AgentEventName` / `AgentInterceptorName`
2. 完成以下 runtime rename：
   - `before_agent_start` -> `prepare_run_input`
   - `before_tool_call` -> `prepare_tool_call`
   - `tool_result_persist` -> `transform_tool_result`
   - `session_start` -> `run_started`
   - `agent_end` -> `run_completed`
   - `session_end` -> 删除
   - `turn_start` -> `turn_started`
   - `turn_end` -> `turn_completed`
   - `after_tool_call` -> `tool_call_completed`
   - `before_compaction` -> `compaction_started`
   - `after_compaction` -> `compaction_completed`
3. 将 runtime/provider 内部事件移出公开类型
4. 新增 `resources/extensions/` 与目录说明
5. 具体扩展场景后续单独建一轮设计

## 五、最终结论

这次收敛不应该只停留在 Hook 改名。  
更合适的方向是：

- **用 Event 表达“发生了什么”**
- **用 Interceptor 表达“允许修改什么”**
- **用 `resources/extensions` 承接内置扩展目录**
- **把具体业务场景留到下一轮单独讨论**

这样扩展系统才能先把底座站稳，而不是被一个还没讨论透的具体场景牵着走。
