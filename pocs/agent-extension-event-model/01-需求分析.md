# Agent 扩展模型收敛 - 需求分析

> 创建时间：2026-04-24
> 状态：设计中
> 优先级：P1（建议在扩展机制真正启用前完成）

## 一、需求背景

当前扩展系统已经从 `src/main/agent/extension` 提升到了 `src/main/extension`，结构上摆脱了“只服务某个运行时目录”的误导，但对外语义仍然不够收敛：

- 同一套 API 里混合了通知事件、可修改拦截点、以及更偏系统集成的注册能力
- Hook 命名风格不统一，`before_* / after_* / *_start / *_end / *_received` 混在一起
- 名字和行为已经出现偏差，例如 `before_compaction` 现在是通知事件，但名字仍然像可拦截控制点
- `session_start / session_end / agent_end` 三者边界不清，容易让人误判真实生命周期
- `message_queued / model_resolved` 这类内部运行时信号，与面向 Agent 的扩展能力混在同一层

除此之外，扩展体系还缺一块很重要的“资源层入口”：

- 目前 `resources/` 下还没有类似旧仓库 `extensions/` 的扩展目录
- 这使得“内置扩展点资源”没有稳定落点
- 一些更适合做成内置扩展的能力，容易被误塞进 runtime hook 体系

这会带来三个直接问题：

1. 扩展作者不知道什么是“稳定的 Agent 扩展面”，什么只是内部实现细节
2. 后续继续演进时，命名会不断拖着旧语义前进，越来越难收
3. 即使我们已经知道要做扩展机制，也没有一个清晰的内置扩展目录可以承接后续落地

## 二、这次明确要做的事情

本轮先明确两件事：

1. **在 `resources/` 下规划并放置一个扩展目录**
   - 作用上类似旧仓库的 `extensions/`
   - 但语义上不再是“任意系统插件”
   - 而是当前仓库内置、受控扩展的目录

2. **把 runtime 扩展面的命名和边界先收干净**
   - 先明确什么是 Event，什么是 Interceptor
   - 先把误导性的历史命名调整到位
   - 具体的第一个业务扩展场景，后续再单独讨论

## 三、核心目标

本次设计希望达成五个目标：

1. **把扩展机制明确收敛到 Agent 层**
   - runtime 扩展面对外表达“Agent 运行过程中发生了什么”
   - 不再默认承载系统插件、通道插件、网关插件的职责

2. **统一命名语义**
   - 通知型能力使用“事件命名”
   - 可修改能力使用“处理点 / 拦截点命名”
   - 避免继续使用会误导语义的 `before_* / after_*`

3. **补上内置扩展目录**
   - 在 `resources/` 下建立稳定扩展入口
   - 让内置扩展不再漂浮在技能目录或运行时代码之外

4. **保留首个业务扩展场景的讨论空间**
   - 本轮先不把某个具体业务场景写死
   - 等场景本身讨论清楚后，再回到扩展设计里落地

5. **为后续实现提供直接落地路径**
   - 当前扩展机制还未被正式使用，因此本次设计**不需要做兼容**
   - 可以直接进行命名调整、目录规划和 API 收口

## 四、当前问题拆解

### 问题 1：事件和拦截点混在一起

当前 `ExtensionHookName` 中同时包含：

- 通知事件：`message_received`、`turn_start`、`after_tool_call`
- 拦截点：`before_agent_start`、`before_tool_call`、`tool_result_persist`
- 内部运行时信号：`message_queued`、`model_resolved`

这导致“注册 hook”这个动作语义过大，开发者需要先记住每个点到底是不是可改写，心智负担很重。

### 问题 2：生命周期命名漂移

当前几个名字容易混淆：

- `session_start / session_end`
- `agent_end`
- `before_agent_start`

从实际代码看，这些点多数围绕一次 Agent 执行过程，而不是“Session 创建 / Session 销毁”本身。  
也就是说，现有命名把“会话生命周期”和“一次执行生命周期”混在了一起。

### 问题 3：通知型事件仍保留控制型前缀

`before_compaction` 已经被调整为纯通知事件，但仍保留 `before_` 前缀。  
这会让阅读者天然预期它可以：

- 阻止默认压缩
- 替换压缩结果
- 接管 compaction 过程

而这已经不成立。

### 问题 4：缺少内置扩展目录

当前 `resources/` 下有：

- `resources/agents`
- `resources/skills`

但没有一个统一的：

- `resources/extensions`

这会造成两个问题：

1. 内置扩展资源没有稳定归属
2. 一些本质上属于“产品扩展能力”的东西，只能硬往 Skill 或 runtime extension 里塞

### 问题 5：首个真实扩展场景尚未定版

我们已经明确：

- 扩展机制要收敛
- `resources/extensions/` 需要建立

但“第一个拿来验证扩展机制的业务场景”本身还没有讨论稳定。  
如果在这个时点把某个具体场景提前写死进 POC，反而容易带偏后续设计。

## 五、设计原则

### 1. 名字必须反映真实能力

- 能改输入的点，不叫 event
- 只做通知的点，不叫 `before_*`
- 生命周期名字要贴近真实语义，而不是历史实现

### 2. 公开面保持小而稳

Agent runtime 扩展面优先服务：

- 上下文注入
- Tool 调用治理
- Turn / Run 生命周期监听
- 压缩、记忆、观察类扩展

不优先服务 runtime 内部排队、provider 选择等实现细节。

### 3. 先把机制边界收干净，再落具体业务场景

如果具体业务场景本身还没讨论清楚，就不应该先反推扩展模型。  
本轮先把边界、命名和目录收干净，具体场景后续再单独推进。

### 4. 内置扩展目录先保持通用

`resources/extensions/` 先作为内置扩展包目录存在。  
至于第一个扩展包到底是什么，本轮暂不固化。

### 5. 不为未使用能力保留历史包袱

由于当前还没有正式依赖这套扩展机制，本次可以直接做：

- 命名调整
- 类型拆分
- 目录规划
- API 收口

而不需要保留 deprecated alias。
