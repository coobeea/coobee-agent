# Agent 扩展模型收敛 - 方案设计

> 创建时间：2026-04-24
> 状态：设计中

## 一、方案概览

这次目标不只是收一批 Hook 名字，而是同时解决两件事：

1. `src/main/extension` 这条 runtime 扩展面怎么收敛
2. `resources/` 下内置扩展目录怎么补齐

当前我们先不把某个具体业务场景写死进设计，而是先把底座做好。  
核心分歧点有三个：

1. 要不要把“事件”和“拦截点”拆开
2. 要不要把 runtime 内部信号继续保留在公开扩展面
3. `resources/extensions/` 应该先做成通用目录，还是一开始就绑定某个具体场景

下面给出三档方案。

## 二、上策：双层扩展架构 + 命名空间化

### 核心思路

彻底把扩展模型拆成两层：

#### 1. Runtime Extension Layer

用于 Agent 运行期扩展：

- **Agent Events**：纯通知，稳定公开
- **Agent Interceptors**：有限的可修改控制点

并进一步命名空间化，例如：

- `run.started`
- `run.completed`
- `turn.started`
- `compaction.started`
- `tool.completed`
- `prepare.run_input`
- `prepare.tool_call`
- `transform.tool_result`

`ExtensionApi` 同步拆分为：

```ts
api.events.on(...)
api.interceptors.use(...)
```

#### 2. Built-in Extension Package Layer

用于当前仓库内置、受控扩展包：

- 根目录：`resources/extensions/`

目录结构示例：

```text
resources/extensions/
  <extension-id>/
    README.md
    prompts/
```

注意：本轮先只定义“这里是内置扩展包目录”，不提前写死第一个扩展包。

### 优势

- 语义最清晰
- runtime 扩展和内置扩展目录彻底分层
- 后续无论首个场景是会话命令、标题策略还是别的能力，都能自然挂上去

### 劣势

- 改动面最大
- 需要一次性重做 API 形态
- 对当前代码来说有点“超前设计”

## 三、中策：runtime 收敛 + `resources/extensions` 通用目录并行引入（推荐）

### 核心思路

保留当前扩展系统主体结构，不做大规模文件级重构，但把架构清晰拆成两块：

#### A. `src/main/extension`

继续作为 **Agent runtime 扩展层**：

1. **通知型能力统一叫 Event**
2. **可修改能力统一叫 Interceptor**
3. **内部运行时信号移出默认公开面**

命名继续沿用 `snake_case`，减少实施阻力。

#### B. `resources/extensions`

新增 **内置扩展目录**：

- 目录位置：`resources/extensions/`
- 当前不绑定具体业务扩展场景

它不承载任意主进程代码，而是先作为：

- 内置
- 受控
- 可演进

的扩展包目录存在。

### 推荐命名（Runtime 扩展层）

#### 1. Interceptor（可修改）

| 现名 | 建议新名 | 说明 |
|------|----------|------|
| `before_agent_start` | `prepare_run_input` | 在 Agent 执行前调整 prompt/system prompt |
| `before_tool_call` | `prepare_tool_call` | 调整参数、阻止调用、挂起审批 |
| `tool_result_persist` | `transform_tool_result` | 在工具结果进入持久化链路前做变换 |

#### 2. Agent Event（公开、稳定）

| 现名 | 建议新名 | 说明 |
|------|----------|------|
| `message_received` | `message_received` | 保留，语义清楚 |
| `session_start` | `run_started` | 实际语义更接近一次执行开始 |
| `agent_end` | `run_completed` | 保留完成结果、时长、成功状态 |
| `session_end` | 删除 | 与 `run_completed` 语义重叠 |
| `turn_start` | `turn_started` | 统一命名风格 |
| `turn_end` | `turn_completed` | 统一命名风格 |
| `after_tool_call` | `tool_call_completed` | 明确是工具调用结果事件 |
| `before_compaction` | `compaction_started` | 已是通知事件，应去掉 `before_` 误导 |
| `after_compaction` | `compaction_completed` | 与开始事件配对 |

#### 3. Runtime Internal Event（不默认公开）

以下点从公开扩展面移出，必要时以后单独作为实验能力回归：

- `message_queued`
- `message_dequeued`
- `queue_drain_start`
- `model_resolved`
- `model_fallback`

### `resources/extensions/` 目录设计

#### 目录结构

```text
resources/
  extensions/
    <extension-id>/
      README.md
      prompts/
```

#### 为什么先只做通用目录

因为当前已经明确要做两件事：

- 先把 runtime 扩展面收干净
- 先把内置扩展目录建起来

但“第一个真实扩展场景”本身还在讨论中。  
如果在这个阶段就把目录结构和场景深度绑定，反而会让文档来回摆动。

#### 后续可以承接什么

后续具体场景讨论清楚后，可以在这个目录下继续增加，例如：

- `session-commands/`
- `memory-thread/`
- `review-summary/`

但本轮不固化。

### API 形态建议（Runtime 扩展层）

即使短期还保留 `api.on()`，类型上也应做拆分：

```ts
type AgentEventName =
  | 'message_received'
  | 'run_started'
  | 'run_completed'
  | 'turn_started'
  | 'turn_completed'
  | 'tool_call_completed'
  | 'compaction_started'
  | 'compaction_completed';

type AgentInterceptorName =
  | 'prepare_run_input'
  | 'prepare_tool_call'
  | 'transform_tool_result';
```

推荐下一步顺手把 API 也往下面这个方向收：

```ts
api.events.on('run_started', handler);
api.interceptors.use('prepare_tool_call', handler, { priority: 10 });
```

但如果想分两步做，也可以先保留：

```ts
api.on('run_started', handler);
api.on('prepare_tool_call', handler);
```

### 事件字段同步收敛建议

命名收敛时，建议顺手把 payload 也一起拉齐：

- 所有耗时字段统一叫 `durationMs`
- `run_started` 补齐 `agentId`
- `run_completed` 直接承接 `agent_end` 的 `success / output / durationMs`
- `compaction_completed.duration` 改为 `durationMs`

### 改动范围

#### Runtime 扩展层

- `src/main/extension/types.ts`
- `src/main/extension/ExtensionApi.ts`
- `src/main/extension/ExtensionHookRunner.ts`
- `src/main/agent/AgentExecutor.ts`
- `src/main/agent/runtime/shared/ToolExecutionPipeline.ts`
- `src/main/agent/provider/*`

#### 内置扩展目录

- `resources/extensions/`
- `resources/extensions/README.md`

#### 文档与示例

- `src/main/agent/README.md`
- 相关 POC / 技能说明 / 测试文档

### 优势

- 命名和真实语义能快速对齐
- 不需要重做整套扩展基础设施
- `resources/extensions` 能立刻成为稳定目录
- 不会因为具体业务场景还没定，就把文档越写越偏

### 劣势

- 仍然保留一部分历史形态
- 首个真实扩展场景需要后续再补一轮设计

## 四、下策：只做局部 Rename

### 核心思路

- 只把 `before_compaction` / `after_compaction` 改掉
- `session_start / session_end / agent_end` 保持不动
- 不拆 Event / Interceptor
- 不补 `resources/extensions/`

### 优势

- 最快
- 改动最小

### 劣势

- 只解决表面问题
- 事件 / 拦截点混杂的问题仍然存在
- `resources/extensions/` 这个关键目录仍然缺位
- 后续具体场景一来，还是要重新翻修

## 五、方案对比

| 维度 | 上策 | 中策 | 下策 |
|------|------|------|------|
| runtime 语义清晰度 | 高 | 高 | 低 |
| 目录结构清晰度 | 高 | 高 | 低 |
| 实施成本 | 高 | 中 | 低 |
| 代码扰动 | 高 | 中 | 低 |
| 长期收益 | 高 | 高 | 低 |
| 适配当前阶段 | 中 | 高 | 低 |

## 六、选定方案

选择 **中策：runtime 收敛 + `resources/extensions` 通用目录并行引入**。

原因：

1. 它已经足够把“纯事件”和“可修改点”分开，能解决当前最大的问题
2. 它能直接回答当前已经明确的需求：扩展目录要有、runtime 边界要清楚
3. 不需要在具体业务场景还没讨论清楚时，提前把文档绑死
4. 当前还没有兼容包袱，可以直接完成 rename、目录规划和资源入口定义
5. 等具体场景讨论稳定后，再挂到这套底座上会更顺
