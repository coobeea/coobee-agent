# Agent 扩展事件模型收敛 - 方案设计

> 创建时间：2026-04-24
> 状态：设计中

## 一、方案概览

本次目标不是只改几个名字，而是把扩展面的语义重新拉直。  
核心分歧点有两个：

1. 要不要把“事件”和“拦截点”拆开
2. 要不要把 runtime 内部信号继续保留在公开扩展面

下面给出三档方案。

## 二、上策：事件 / 拦截点双通道 + 命名空间化

### 核心思路

彻底把扩展面拆成两类：

- **Agent Events**：纯通知，稳定公开
- **Agent Interceptors**：有限的可修改控制点

同时将命名进一步命名空间化，例如：

- `run.started`
- `run.completed`
- `turn.started`
- `compaction.started`
- `tool.completed`
- `prepare.run_input`
- `prepare.tool_call`
- `transform.tool_result`

`ExtensionApi` 也同步拆分为：

```ts
api.events.on(...)
api.interceptors.use(...)
```

### 改动范围

- 重写 `ExtensionHookName` 建模方式
- `ExtensionApi` 从 `on()` 改为 `events.on()` / `interceptors.use()`
- `ExtensionRegistry`、`ExtensionHookRunner` 按类别拆分
- 全部调用点改名
- 文档、示例、测试全量更新

### 优势

- 语义最清晰
- 对外能力边界非常稳
- 后续扩展 SDK 时可直接复用这个模型

### 劣势

- 改动面最大
- 需要一次性重做 API 形态
- 对当前代码来说有点“超前设计”

## 三、中策：保留单入口，但按语义拆成 Event / Interceptor 两层（推荐）

### 核心思路

保留当前扩展系统主体结构，不做大规模文件级重构，但在类型和命名上明确拆分：

1. **通知型能力统一叫 Event**
2. **可修改能力统一叫 Interceptor**
3. **内部运行时信号移出默认公开面**

命名仍然采用现有代码风格的 `snake_case`，减少实施阻力。

### 推荐命名

#### 1. Interceptor（可修改）

| 现名 | 建议新名 | 说明 |
|------|----------|------|
| `before_agent_start` | `prepare_run_input` | 在 Agent 执行前调整 prompt/system prompt |
| `before_tool_call` | `prepare_tool_call` | 调整参数、阻止调用、挂起审批 |
| `tool_result_persist` | `transform_tool_result` | 在工具结果进入持久化链路前做变换 |

#### 2. Agent Event（公开、稳定）

| 现名 | 建议新名 | 说明 |
|------|----------|------|
| `message_received` | `message_received` | 保留，语义清楚 |
| `session_start` | `run_started` | 实际语义更接近一次执行开始 |
| `agent_end` | `run_completed` | 保留完成结果、时长、成功状态 |
| `session_end` | 删除 | 与 `run_completed` 语义重叠 |
| `turn_start` | `turn_started` | 统一命名风格 |
| `turn_end` | `turn_completed` | 统一命名风格 |
| `after_tool_call` | `tool_call_completed` | 明确是工具调用结果事件 |
| `before_compaction` | `compaction_started` | 已是通知事件，应去掉 `before_` 误导 |
| `after_compaction` | `compaction_completed` | 与开始事件配对 |

#### 3. Runtime Internal Event（不默认公开）

以下点从公开扩展面移出，必要时以后单独作为实验能力回归：

- `message_queued`
- `message_dequeued`
- `queue_drain_start`
- `model_resolved`
- `model_fallback`

### API 形态建议

即使短期还保留 `api.on()`，类型上也应做拆分：

```ts
type AgentEventName =
  | 'message_received'
  | 'run_started'
  | 'run_completed'
  | 'turn_started'
  | 'turn_completed'
  | 'tool_call_completed'
  | 'compaction_started'
  | 'compaction_completed';

type AgentInterceptorName =
  | 'prepare_run_input'
  | 'prepare_tool_call'
  | 'transform_tool_result';
```

推荐下一步顺手把 API 也往下面这个方向收：

```ts
api.events.on('run_started', handler);
api.interceptors.use('prepare_tool_call', handler, { priority: 10 });
```

但如果想分两步做，也可以先保留：

```ts
api.on('run_started', handler);
api.on('prepare_tool_call', handler);
```

### 事件字段同步收敛建议

命名收敛时，建议顺手把 payload 也一起拉齐：

- 所有耗时字段统一叫 `durationMs`
- `run_started` 补齐 `agentId`
- `run_completed` 直接承接 `agent_end` 的 `success / output / durationMs`
- `compaction_completed.duration` 改为 `durationMs`

### 改动范围

- `src/main/extension/types.ts`
- `src/main/extension/ExtensionApi.ts`
- `src/main/extension/ExtensionHookRunner.ts`
- `src/main/agent/AgentExecutor.ts`
- `src/main/agent/runtime/shared/ToolExecutionPipeline.ts`
- `src/main/agent/provider/*`
- 文档、技能说明、测试

### 优势

- 命名和真实语义能快速对齐
- 不需要重做整套扩展基础设施
- 便于逐步把 `api.on()` 迁移成更清晰的双入口 API
- 很适合当前“尚未正式对外使用”的状态

### 劣势

- 仍然保留一部分历史形态
- `snake_case` 事件名不如命名空间格式那么强表达

## 四、下策：只做局部 Rename

### 核心思路

只修最明显的不一致：

- `before_compaction` -> `compaction_started`
- `after_compaction` -> `compaction_completed`
- `session_start / session_end / agent_end` 保持不动
- 不拆 Event / Interceptor

### 改动范围

- 只改少量类型和调用点

### 优势

- 见效快
- 改动小

### 劣势

- 只解决表面问题
- 事件 / 拦截点混杂的问题仍然存在
- `session_*` 与 `agent_end` 的混乱继续保留

## 五、方案对比

| 维度 | 上策 | 中策 | 下策 |
|------|------|------|------|
| 语义清晰度 | 高 | 高 | 低 |
| 实施成本 | 高 | 中 | 低 |
| 代码扰动 | 高 | 中 | 低 |
| 长期收益 | 高 | 高 | 低 |
| 适配当前阶段 | 中 | 高 | 中 |

## 六、选定方案

选择 **中策：保留单入口，但按语义拆成 Event / Interceptor 两层**。

原因：

1. 它已经足够把“纯事件”和“可修改点”分开，能解决当前最大的问题
2. 不需要一次性把扩展系统完全重做，实施风险更低
3. 当前还没有兼容包袱，可以直接完成 rename 和收口
4. 以后如果要继续升级成 `api.events.on / api.interceptors.use`，中策是最自然的跳板
