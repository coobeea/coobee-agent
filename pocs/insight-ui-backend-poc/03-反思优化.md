# Insight UI + Backend POC - 反思优化

> 创建时间：2026-04-24
> 选定方案：中策（最小闭环 POC）

## 边界情况

1. 当前项目虽然已有 `src/shared/types/insight.ts`，但并不代表这些字段已经完全适合真实落地，尤其是会话状态、快照触发类型、结果结构可能还需要小幅补充。
2. 参考项目中包含录音模式、静默触发、配置面板、模板编辑等能力；当前项目首轮 POC 不应一次性全部照搬。
3. 如果第一阶段就做自动触发和多状态切换，容易在没有稳定主链路时引入额外复杂度。

## 安全评估

1. Insight 分析本质上会处理较长文本，会带来潜在敏感信息落盘风险。
2. 如果后续允许前端直接提交大段转写文本，后端需要限制长度、频率和存储策略。
3. 如果通过 Agent/Channel 执行分析，需要明确 prompt 来源和日志边界，避免把用户原文不必要地扩散到调试输出。

## 影响分析

1. 新增模块主要集中在 `src/main/insight`、`src/main/gateway/http`、`src/renderer/src/views|api|components`，对现有 Agent 主链路影响可控。
2. 与现有代码最直接的耦合点在：
   - 路由注册
   - Gateway HTTP 注册
   - Agent/Channel 分析调用
   - 前端侧边栏和页面路由
3. 如果共享类型调整过大，可能影响后续实现与参考项目之间的迁移一致性，因此应优先做“增量补充”而非“推翻重写”。

## 性能与可维护性

1. 首轮 POC 采用“手动触发分析 + 快照落盘”更利于控制复杂度。
2. 自动触发和高频轮询如果过早引入，会增加分析压力、状态同步复杂度和前端刷新噪音。
3. 模块边界建议尽量保持与参考项目一致，这样后续从参考实现中借鉴代码和测试会更顺畅。

## 优化调整

1. 第一阶段只实现 `manual` 触发，`content` / `silence` 作为后续增强项。
2. 第一阶段只提供内置模板读取，不做模板编辑和用户模板持久化。
3. 第一阶段优先做 HTTP 拉取，不直接上 WebSocket 推送。
4. 第一阶段历史详情页可只支持“按快照回看”，不必做复杂筛选。

## 最终方案

采用“参考项目架构 + 当前项目最小闭环”的落地策略：

1. 保留参考项目的核心模块边界：
   - 路由层
   - 编排器
   - 模板存储
   - 会话管理
   - 快照存储
   - 分析执行器
2. 在当前项目中分两步推进：
   - 第一步：手动分析闭环
   - 第二步：自动触发和更完整的会话能力
3. 所有新增接口、文件和 TODO 都围绕当前项目目录结构展开，不直接照搬参考项目路径。
