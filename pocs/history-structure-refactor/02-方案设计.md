# history.jsonl 结构重构 - 方案设计

> 创建时间：2026-04-24

## 目标导向

本次重构只服务一个目标：让 `history.jsonl` 成为前端可直接消费的、一次用户请求对应一条 assistant 记录的 v2 投影。

不做旧格式兼容，不做历史迁移，不在前端保留两套读取逻辑。旧 `history.jsonl` 数据由上线或测试前手动删除，删除后新产生的数据统一使用 v2 结构。

## 推荐方案：Run 级聚合 + v2 单格式

### 核心思路

1. `HistoryWriter` 监听 `run:start` 初始化一条 assistant 聚合记录。
2. `turn:start` 创建一个 `TurnRecord`，追加到当前 run 的 `turns[]`。
3. `reasoning:delta`、`text:delta`、`tool:start`、`tool:done`、`llm:done` 都写入当前 turn。
4. `turn:done` 只结束当前 turn，不写盘。
5. `run:done` 一次性写入完整 assistant 记录到 `history.jsonl`。
6. 顶层保留前端常用字段：`id`、`role`、`timestamp`、`content`、`usage`、`startTime`、`endTime`。
7. 内部通过 `turns[]` 保留每次 LLM 调用的边界、工具调用和 token 明细。

### v2 数据结构

```json
{
  "version": 2,
  "id": "assistant-xxx",
  "role": "assistant",
  "timestamp": "2026-04-24T07:16:11.697Z",
  "startTime": "2026-04-24T07:16:11.697Z",
  "endTime": "2026-04-24T07:16:46.710Z",
  "status": "done",
  "content": "最终回复内容",
  "turns": [
    {
      "index": 1,
      "startTime": "2026-04-24T07:16:11.697Z",
      "endTime": "2026-04-24T07:16:24.222Z",

      "content": "",

        {
```

### 关键语义

- `history.jsonl` 是前端展示投影，不是完整事件源。
- 一次用户请求写入一条 user 消息和一条 assistant v2 消息。
- assistant 顶层 `content` 是所有 turns 的最终可展示文本汇总。
- assistant 顶层不保存 `reasoning`，历史恢复时按 `turns[].reasoning` 分别展示每轮思考。
- assistant 顶层 `usage` 是所有 `llm:done` usage 的汇总。
- `turns[]` 用于审计和调试，不要求前端基础渲染遍历它。
- 旧格式不进入读取链路，发现非 v2 assistant 记录可以视为无效数据。

## 为什么不做兼容

1. **用户目标是修正结构，不是平滑迁移旧数据**：旧数据会直接删除，兼容逻辑没有实际收益。
2. **兼容会污染前端模型**：`if (msg.turns) ... else ...` 会让历史包袱长期留在渲染层。
3. **测试范围会被无效放大**：新旧混合、迁移、降级读取都不是当前问题的核心。
4. **v2 契约越明确，后续维护越简单**：所有读写路径只围绕一种结构验证。

## 改动范围

### 主进程

- `src/main/agent/streaming/consumers/HistoryWriter.ts`
  - 从 `currentTurns` 改为 `currentRun`
  - `turn:done` 不写盘
  - `run:done` 写入完整 v2 assistant 记录
  - `run:error` / `stop()` 时尽量 flush 未完成 run

- `src/main/agent/streaming/consumers/RunAggregator.ts`
  - 可选新增，用于封装 run/turn 聚合逻辑
  - 如果实现足够简单，也可以先内聚在 `HistoryWriter.ts` 中，避免为了抽象而抽象

- `src/main/agent/streaming/types.ts`
  - 定义 `HistoryMessageV2`、`TurnRecord`、`ToolCallRecord`、`UsageRecord`

### 渲染进程

- `src/renderer/src/components/agent/ChatPanel.vue`
  - 历史加载只按 v2 结构解析 assistant
  - 使用顶层 `content`、`usage`
  - 每个 `turn.reasoning` 分别恢复为独立 thinking block
  - 工具展示可从 `turns[].toolCalls` 展平得到

- `src/renderer/src/types/chat.ts`
  - 补充前端消费 v2 history 所需类型

### 路由

- `src/main/routes/ThreadRoutes.ts`
  - 读取 `history.jsonl` 并返回原始 v2 消息
  - 不承担旧格式适配职责

### 测试

- 单 run 单 turn：生成一条 assistant v2 记录。
- 单 run 多 turn：只写一条 assistant v2 记录，`turns.length > 1`。
- 多次 `llm:done`：顶层 `usage` 等于所有 turn usage 之和。
- 工具调用：`tool:start/tool:done` 能落入对应 turn 的 `toolCalls`。
- 前端历史加载：v2 assistant 能正确恢复为 `StreamChatMessage`。

## 不做范围

- 不迁移旧 `history.jsonl`。
- 不兼容旧 assistant 记录。
- 不支持新旧格式混读。
- 不新增历史格式迁移指南。
- 不把敏感字段脱敏作为本次 POC 的必须项，除非后续单独立项。

## 风险与处理

### 1. 当前事件没有稳定 runId

现有 `run:start` 事件没有稳定 `runId` 字段，`StreamMessage.id` 是事件级 id，不能代表 run。

处理方式：

- 当前实现如果同一个 session 不允许并发 run，则 `currentRuns` 可以按 `sessionId` 管理。
- 如果产品允许同一 session 并发 run，需要先在事件协议补充真正的 `runId`，再用 `${sessionId}:${runId}` 作为 key。
- 不使用 timestamp 拼 runId 作为并发正确性的基础。

### 2. run 未正常结束

处理方式：

- `run:error` 时写入 `status: "error"` 的 v2 assistant。
- `HistoryWriter.stop()` 时 flush 当前未完成 run，写入 `status: "interrupted"`。
- 第一阶段不做复杂定时清理，除非验证存在长期后台运行导致的内存泄漏。

### 3. 前端历史为空

旧数据删除后，旧 thread 可能没有历史消息。

处理方式：

- 前端按空历史展示即可。
- 不为了旧 thread 恢复展示增加兼容分支。

## 选定方案

**选择：Run 级聚合 + v2 单格式**

这是最贴近目标的方案：解决“实时一条、重载多条”的展示问题，保留多 turn 和 usage 明细，同时避免旧格式兼容带来的额外复杂度。
