# history.jsonl 结构重构 - 反思优化

> 创建时间：2026-04-24  
> 选定方案：Run 级聚合 + v2 单格式

## 核心判断

原方案的方向是正确的：`history.jsonl` 应从 turn 级记录改为 run 级 assistant 聚合记录。

需要调整的是复杂度边界：既然旧数据会直接删除，本次方案不应该设计旧格式兼容、迁移脚本、新旧混合测试，也不应该让前端长期保留两套解析逻辑。

## 边界情况

### 1. 当前事件没有稳定 runId

**现状**：`run:start` 事件当前没有稳定 `runId`，事件自身的 `message.id` 是每个事件独立生成的 id，不能代表一次 run。

**风险**：如果用 timestamp 或事件 id 拼接 run key，会制造一种“看起来支持并发”的假象，但并不能可靠关联后续 `turn:*`、`llm:*`、`run:done`。

**处理**：

- 第一阶段按当前运行模型处理：同一个 session 同一时间只维护一个 active run，key 使用 `sessionId`。
- 如果后续确认同一 session 需要并发 run，先改事件协议，为 `run:start`、`turn:*`、`llm:*`、`run:done` 全链路补充真实 `runId`。
- 不用 timestamp 作为并发正确性的基础。

### 2. run:start 后没有 run:done

**场景**：应用崩溃、用户强制关闭、运行时异常导致 run 未正常结束。

**风险**：当前 run 留在内存中，没有写入 `history.jsonl`。

**处理**：

- `run:error` 时立即 finalize，写入 `status: "error"`。
- `HistoryWriter.stop()` 时 flush 当前未完成 run，写入 `status: "interrupted"`。
- 暂不引入定时清理器；只有在验证存在长期后台运行泄漏时再加。

### 3. turn:start 后没有 turn:done

**场景**：模型调用或工具执行中断。

**风险**：最后一个 turn 缺少 `endTime` 和明确状态。

**处理**：

- `run:done`、`run:error`、`stop()` finalize 时检查当前 turn。
- 若当前 turn 未结束，补 `endTime`，并标记 `status: "interrupted"` 或继承 run 的错误状态。

### 4. turns 为空

**场景**：`run:start` 后立即异常，没有任何 turn 事件。

**处理**：

- 如果没有任何内容、工具、usage，可不写 assistant 记录。
- 如果存在错误信息，则写入 `status: "error"` 且 `turns: []`，前端按错误消息展示。

### 5. 旧 history 数据

**处理**：不处理。实施前直接删除旧 `history.jsonl` 数据，新数据统一 v2。

## 安全评估

### 注入风险

`history.jsonl` 使用 `JSON.stringify` 按行写入，前端 Vue 渲染默认转义，当前重构不新增额外注入面。

### 敏感信息

工具参数和工具结果可能包含敏感内容，但这不是本次结构重构的核心目标。

本次不把脱敏列为必须项，原因：

- 当前 `history.jsonl` 本来已经记录工具结果，风险不是由 v2 引入。
- 脱敏策略需要单独定义字段规则、深层对象处理、白名单/黑名单语义，容易扩大范围。
- 若要做，应单独立项为“history 敏感信息治理”。

## 影响分析

### 主进程

`HistoryWriter` 的写入时机从 `turn:done` 改为 `run:done`，这是本次核心变化。

预期收益：

- 一次用户请求只生成一条 assistant 记录。
- 多个 turn 的 token 和工具调用都能保留。
- 磁盘写入次数减少。

主要风险：

- run 生命周期管理比 turn 生命周期更复杂。
- 未完成 run 需要在错误或停止时收口。

### 前端

前端历史加载只需要消费 v2：

- 顶层 `content` 生成 text block。
- 每个 `turn.reasoning` 分别生成独立 thinking block，保留多轮推理边界。
- `turns[].toolCalls` 展平成 tool blocks。
- 顶层 `usage` 生成 stats。

运行时流式展示仍可保持现有逻辑，不要求和落盘结构完全相同。

### 路由

`ThreadRoutes.ts` 不做结构转换，只读取并返回 `history.jsonl` 中的 v2 消息。

### 旧 Thread

旧数据被删除后，旧 thread 没有历史消息是预期结果，不为此增加兼容逻辑。

## 复杂度收敛

### 保留

- v2 明确结构。
- run 级聚合。
- 顶层 `content` / `usage` 汇总。
- `turns[]` 保存审计明细。
- 必要的错误和 interrupted 收口。
- 聚焦测试：单 turn、多 turn、工具、usage、前端恢复。

### 删除

- 旧格式兼容读取。
- 新旧格式混合测试。
- 历史迁移脚本。
- 迁移指南。
- 强制 95% 覆盖率目标。
- 第一阶段定时清理器。
- 第一阶段敏感字段脱敏。

## 最终方案

1. `history.jsonl` 只写 v2。
2. 旧 `history.jsonl` 在实施或验证前直接删除。
3. `HistoryWriter` 以 session 当前 active run 为单位聚合。
4. `run:done` 写入完整 assistant v2 记录。
5. `run:error` / `stop()` 对未完成 run 做最小可靠收口。
6. 前端历史加载只按 v2 结构解析。

这个方案更贴近当前目标：修正 history 结构，而不是建立一套长期格式兼容系统。
