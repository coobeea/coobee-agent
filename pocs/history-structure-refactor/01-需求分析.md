# history.jsonl 结构重构 - 需求分析

> 创建时间：2026-04-24

## 需求背景

当前 `history.jsonl` 是按 `turn` 粒度写入的，每次 `turn:start/turn:done` 之间写一条 assistant 记录。这种设计存在以下问题：

1. **语义混乱**：`turn`、`assistant 消息`、`llm 调用` 三个概念混在一起，前端运行态按 `run` 聚合，但落盘态却按 `turn` 分条，导致"实时展示一条，重新加载变多条"
2. **多轮调用边界丢失**：一个 turn 里如果有多次 LLM 调用，只有最后一次 `llm:done` 的 token 统计被保留，无法还原完整调用链路
3. **前端消费困难**：前端需要遍历所有 turn 的 content 拼接才能得到最终回复，没有直接可用的顶层字段
4. **缺少审计能力**：无法从 history 直接看出一次对话里发生了几次模型调用、每次调用的 token 消耗

底层的 `events.jsonl` 和 `sessions/*.jsonl` 都有完整事件链路，但 `history.jsonl` 作为前端投影，现在既不够简洁（多条拆分），又不够完整（丢失调用细节）。

## 核心目标

重新定义 `history.jsonl` 的语义和结构，使其：

1. **语义统一**：明确 `history.jsonl` 是"一次用户请求的完整记录"，而不是"每个 turn 一条记录"
2. **结构分层**：顶层是 run/assistant 消息，内部嵌套 `turns[]`，每个 turn 包含 `status/reasoning/content/toolCalls/usage`
3. **前端友好**：提供顶层汇总字段（如 `content/usage`），前端无需遍历内部结构即可完成基础文本和统计渲染
4. **可审计可回放**：保留多轮调用的边界和明细，支持从 history 直接分析调用链路

## 约束条件

1. **格式要求**：新 `history.jsonl` 只支持 v2 结构，不兼容旧 assistant 记录
2. **性能约束**：`HistoryWriter` 是异步批量写入，不能引入同步阻塞或过度复杂的聚合逻辑
3. **存量数据**：旧 `history.jsonl` 数据由实施前直接删除，不迁移、不混读
4. **实施成本**：优先考虑最小改动方案，在当前 `HistoryWriter` 基础上调整，而不是推倒重写

## 最终目标结构

```json
{
  "version": 2,
  "id": "assistant-xxx",
  "role": "assistant",
  "timestamp": "2026-04-24T07:16:11.697Z",
  "startTime": "2026-04-24T07:16:11.697Z",
  "endTime": "2026-04-24T07:16:46.710Z",
  "status": "done",
  "content": "最终回复内容",
  "turns": [
    {
      "index": 1,
      "startTime": "2026-04-24T07:16:11.697Z",
      "endTime": "2026-04-24T07:16:24.222Z",
      "status": "done",
      "reasoning": "...",
      "content": "",
      "toolCalls": [
        {
          "name": "skill_list",
          "callId": "call_jf7s83f3",
          "arguments": {},
          "result": "...",
          "status": "done",
          "startTime": "2026-04-24T07:16:24.221Z",
          "endTime": "2026-04-24T07:16:24.222Z"
        }
      ],
      "usage": {
        "inputTokens": 3556,
        "outputTokens": 78,
        "totalTokens": 3634
      }
    }
  ],
  "usage": {
    "inputTokens": 9495,
    "outputTokens": 1000,
    "totalTokens": 10495
  }
}
```

### 核心特点

1. 顶层保留 `id/role/timestamp`，并增加 `version: 2` 明确新格式契约
2. `turns[]` 按 turnIndex 记录每轮调用
3. 顶层 `content` 是最终可展示回复，不在顶层重复保存 `reasoning`
4. 每个 turn 有独立的 `status/reasoning/content/toolCalls/usage`
5. 顶层 `usage` 是所有 turn 的汇总
6. 顶层和 turn 都有 `status`，用于标记 `done/error/interrupted`
7. 时间戳分为 `timestamp`（展示排序字段）、`startTime/endTime`（精确范围）
