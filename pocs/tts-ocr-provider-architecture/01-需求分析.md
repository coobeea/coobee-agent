# TTS OCR Provider 架构拆分 - 需求分析

> 创建时间：2026-05-04

## 需求背景

当前 `resources/workers/tts/server.py` 和 `resources/workers/ocr/server.py` 仍然采用单文件承载多职责的实现方式：

- Worker 启动与健康检查
- 运行时配置读取
- 本地模型加载
- 在线 provider 接入
- `/api/test` 测试逻辑
- WebSocket 会话处理
- 不同模型分支判断

而 `asr` 已经完成了“入口层 + 通用层 + provider 层”的拆分，具备更清晰的边界。现在用户要求把 `tts` 和 `ocr` 也整理成与 `asr` 一样的架构，避免继续在单个 `server.py` 中堆叠不同模型和不同协议。

## 核心目标

- 将 `tts` 和 `ocr` 拆成与 `asr` 一致的 provider 架构
- 让 `server.py` 只保留入口编排、路由分发和应用启动
- 将本地模型、在线模型、不同协议实现迁移到独立 provider 文件
- 为后续新增模型保留统一扩展点，避免继续加 `if/elif` 分支

## 约束条件

- 不能破坏当前前端依赖的 Worker 路由：
  - `tts`：`/health`、`/api/test`、`/api/tts`、`/ws/tts`、`/api/speakers`
  - `ocr`：`/health`、`/api/test`、`/api/ocr`、`/ws/ocr`
- 不能改变当前运行时配置协议：
  - `model_name`
  - `model_credentials[model_name].api_key`
- 不能在这一步同时大改设置页和模型列表协议
- OCR 后续验证不跑本地模型，只保留在线链路验证
- 要兼容当前已有模型：
  - `tts`：本地 Qwen3 TTS、Edge TTS、阿里云 Qwen TTS Realtime、阿里云 CosyVoice
  - `ocr`：本地 GLM-OCR、PaddleOCR、AI Studio Layout Parsing

## 涉及范围

- 模块：
  - TTS Worker
  - OCR Worker
  - provider 注册与选择
  - 配置读取与 provider 判断
- 文件：
  - `resources/workers/tts/server.py`
  - `resources/workers/ocr/server.py`
  - 后续新增 `resources/workers/tts/{app,core,providers}/*`
  - 后续新增 `resources/workers/ocr/{app,core,providers}/*`
- 接口：
  - `tts` 的 HTTP / WebSocket 接口
  - `ocr` 的 HTTP / WebSocket 接口
  - provider 内部抽象接口

## 需求本质

这次需求的本质不是简单把文件拆小，而是让 `tts` 和 `ocr` 都形成和 `asr` 一致的架构约束：

- 入口层：只负责路由、启动、选择当前 provider
- 通用层：只负责配置、日志、公共工具
- 实现层：每个 provider 各自封装模型加载、测试和请求处理

如果不把这个边界立住，后续再加新的 TTS/OCR 在线模型时，逻辑还会继续堆回 `server.py`。
