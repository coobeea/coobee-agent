# TTS OCR Provider 架构拆分 - 反思优化

> 创建时间：2026-05-04
> 选定方案：中策

## 边界情况

- `tts` 存在 4 类后端：
  - 本地 Qwen3 TTS
  - Edge TTS
  - 阿里云 Qwen TTS Realtime
  - 阿里云 CosyVoice
- `ocr` 当前只有 2 类后端：
  - 本地 OCR
  - AI Studio 在线 OCR
- `ocr` 的 `PaddleOCR-V5` 当前仍映射到本地链路，本轮不额外新增独立 provider，只保留扩展点

## 安全评估

- provider 拆分后不能破坏现有 `api_key` 读取逻辑
- 在线 provider 的日志不能输出明文密钥
- 拆分时不能把不同 provider 的异常吞掉，否则会增加排障成本

## 影响分析

- 前端设置页理论上不需要改，因为路由和 `models.json` 不变
- `WorkerManager` 不需要改，因为入口仍是各自的 `server.py`
- 风险主要集中在：
  - `tts` 的 `/api/tts` 和 `/ws/tts`
  - `ocr` 的 `/api/ocr` 和 `/ws/ocr`

## 性能与可维护性

- provider 拆分本身不会增加显著运行时成本
- 主要收益是后续新增模型时只需要：
  - 新增 provider 文件
  - 注册 provider
  - 绑定模型选择逻辑
- `server.py` 缩小后，启动入口、健康检查和测试逻辑会更容易验证

## 优化调整

- 不强求 `tts` 和 `ocr` 在第一轮就完全复制 `asr/core/` 的目录数量
- 先确保最关键的两层具备：
  - `providers/base.py`
  - `app/provider_registry.py`
- 如确有必要，再补 `core/config.py` 或 `core/utils.py`，避免为了“形似”而过度拆分

## 最终方案

最终采用“与 `asr` 同构，但不过度共享”的拆分方式：

- `tts`
  - 新增 `providers/base.py`
  - 新增 `providers/local_provider.py`
  - 新增 `providers/edge_provider.py`
  - 新增 `providers/aliyun_qwen_provider.py`
  - 新增 `providers/aliyun_cosyvoice_provider.py`
  - 新增 `app/provider_registry.py`
- `ocr`
  - 新增 `providers/base.py`
  - 新增 `providers/local_provider.py`
  - 新增 `providers/aistudio_provider.py`
  - 新增 `app/provider_registry.py`
- 两个 `server.py` 都只保留：
  - 配置加载
  - provider registry 构建
  - 当前 provider 选择
  - FastAPI 路由入口
